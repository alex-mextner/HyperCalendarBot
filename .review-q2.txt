In hypercalendarbot's intent workflow DSL (src/services/intent/workflow-schema.ts + workflow-validator.ts + variable-resolver.ts), I found that tool input values must always be JSON strings in the stored workflow (ToolInputSchema = z.record(z.string(), z.string())), and resolveVariables() never produces a genuine number from a literal template — only dates/captures/stepResults which are either strings or come from actual runtime data. The get_holidays tool's real input schema (src/services/ai/tool-schemas.ts) is z.object({ limit: z.number().optional() }) with NO z.coerce — so a workflow literally cannot pass a non-default numeric limit to get_holidays; passing "1" or "5" as a string fails dispatch, and a raw JSON number in the stored workflow fails WorkflowSchema itself at match time (I verified both against the real zod schemas). Given this, I designed 5 separate holiday intents (show_upcoming_holidays, show_next_public_holiday, is_today_public_holiday, show_holidays_this_month, show_holidays_this_year — see scripts/seed-intents-holidays-and-info.ts) that ALL call get_holidays with an empty input (relying on its default: top 10 results, ~365-day lookahead), differentiated only by which RU/EN phrasings/trigger-words route to them — not by any difference in actual behavior. Is this the right design choice for maximizing deterministic phrase coverage of common holiday questions given the tool's hard limitation, or should some of these be merged/dropped as misleading/redundant? Consider specifically: is_today_public_holiday and show_next_public_holiday return the exact same generic "here are the upcoming holidays" list rather than a targeted yes/no or single-item answer — is that an acceptable UX degradation given it matches what the AI agent itself would produce today, or does it cross into "phrase implies functionality the workflow doesn't deliver" and should be cut? Give a definitive recommendation with reasoning, not just pros/cons.
