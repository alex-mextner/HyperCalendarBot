# Secretary invitation incident closeout — 2026-10-31

Scope: one private conversation in which a write-secretary asked the bot to create an event in the owner's calendar and invite named people. Evidence came from the per-chat AI debug log and the Docker log (procedure: AGENTS.md "Analyzing a problem", `docs/reference/deploy-runbook.md` Diagnostics). No private messages, names, titles or ids are recorded here or in the linked issues.

## Root causes

1. **ask_user never reached the user (#908).** A 45-character Russian option is 87 bytes in `ai_btn:<text>`; Telegram refuses `callback_data` over 64 bytes (`BUTTON_DATA_INVALID`), so the whole question failed to send and the model got an error it could not act on.
2. **A write-secretary could not invite for the owner's events (#909).** `send_invitation` had no `owner_id`, so a secretary could not address an event in the owner's calendar. Recipient identity is unchanged in principle: invented ids are still refused by the existing verification; the change only treats the requester's own id as verified and adjusts the rejection hints for delegated calendars.
3. **The receipt after the partly failed run was unreadable (#526).** The turn-finish guard replaced the model's text with the `Попытка N` attempt ledger, so the user could not tell what was actually done.

## Review findings fixed in the pre-commit review round (2026-10-31)

- ask_user: an option of any length became `ai_opt:<index>`, and the acknowledgement edit (`question + ✅ answer`) then failed past 4096 characters with the failure swallowed, so a second tap was not seen as answered and the AI got two continuations. Fixed in the tap handler (answer-only fallback, answers shortened to one bounded line, the answered message remembered in process memory so a failed edit or two racing taps reach the AI once). No label-length or keyboard-size limit is enforced: the 200-character and 10 KB checks were guesses and were removed; `ask_user` still rejects an empty question or option and more than 100 buttons. Whether Telegram carries a very long button label whole is still unverified (#914). Regression tests: `test/services/ai/tool-handlers/ask-user.test.ts`, `test/bot/handlers/ai-button-answers.test.ts`.
- Secretary invitations (#909): delegated paths looked the event up with `getEvent`, which also returns events visible through group membership, so a secretary could act on a group event the owner does not organise. They now use an owner-only personal-event lookup. Write access is re-checked after the awaited recipient lookup (a revoked secretary can no longer send or resend), and the event is re-read after the lookup so the card shows current details. **Behaviour change:** a secretary can no longer act on group-owned events, only on the owner's personal events. Tests: `test/services/ai/tool-handlers/sharing-secretary-invitation-scope.test.ts`.
- Receipt (#526): a parseable non-ISO `start_at` from a rejected create threw `RangeError` while rendering the receipt; the create identity lacked calendar scope and recurrence, so a failed group or recurring create was folded behind a personal success; markup in event titles and names could break the delivered message. The receipt now never throws on such input, keeps those creates apart and neutralises markup in names. Tests: `test/services/ai/write-receipt.test.ts`, `test/services/ai/write-outcomes.test.ts`.
- AGENTS.md log procedure: no private chat id (use `<chatId>`), no whole-log `cat` (copy to a 0600 temp file, read ranges, delete), docker filter also shows level-30 delivery records (FINAL is recorded before delivery), anonymized excerpts only; the runbook commands changed to match.

## Review findings fixed in the second review round (2026-10-31)

1. ask_user single continuation (#908): the callback handler is built anew for every update (`src/bot/index.ts`), so the answered-message set inside it was empty on each tap; it is now one bounded process-wide set in `src/bot/handlers/callback/ai-routes.ts` (the bot is one container, and the in-memory delete-confirmation store follows the same convention). Test: a failed acknowledgement edit, then a second tap on a fresh handler, reaches the AI once (`test/bot/handlers/ai-button-answers.test.ts`).
2. `cancel_invitation` and `resend_invitation` (#909): the delegated cancel guard looked up the event of an invitation id before checking its inviter, so a secretary of owner A could learn that owner B's invitation exists and which event it names; and for every caller a foreign id answered `Not authorized to cancel` / `Not your invitation.` while a missing one answered `Invitation not found`, an existence oracle. Both tools now check the inviter first and answer a foreign id exactly as a missing one (`Invitation not found`), for the owner path too; `get_invitation_status` stays with #915. Tests: `test/services/ai/tool-handlers/sharing-secretary-invitation-scope.test.ts`, `test/services/ai/tool-handlers/sharing-failure-paths.test.ts` (the pinned `Not your invitation.` wording changed).
3. Group event the managed owner created (#909): the error still said `Retry with owner_id N` after `owner_id` was supplied. It is now an explicit scope denial (a secretary acts only on the owner's personal events) with no retry hint; the hint stays for a personal event when `owner_id` was forgotten. Same test file.
4. Receipt create identity (#526): the raw RRULE string was part of the key, so `FREQ=WEEKLY;BYDAY=MO` and `BYDAY=MO;FREQ=WEEKLY` were two events and the receipt said both "Not created" and "Created". The recurrence is normalised (part order, list order, case, spacing, `RRULE:` prefix, default `INTERVAL=1`); a different interval, weekday set, count or nth weekday stays distinct. Test: `test/services/ai/write-outcomes.test.ts`.
5. Log rule (#908): AGENTS.md treated a missing level-30 delivery record as failure. A successful `ask_user` send logs none, and an ordinary reply logs `AI request metric`, which the runbook filter dropped. A missing record is now unknown, not failure, and the rule names the records that exist (`AI request metric` with `deliveryOutcome`, `Finalize edit failed`, `Finalize send failed`, `Writer finalize failed`, `Delivered via ...`, `deep-link fallback attempted`, `Delivery chain failed`); the runbook filter was widened to match.
6. Private log copy (#908): the runbook used a bare `mktemp`, which honours `TMPDIR` (with `TMPDIR=.` the copy would land in the checkout). AGENTS.md and the runbook use `umask 077; mktemp /tmp/hcb-chat.XXXXXX`.
7. ask_user claim lost on a failed tap (#908): the answered-message claim was made before `ctx.answer()`, so an `answer()` failure (callback query too old, network) skipped the acknowledgement and the AI continuation while the message stayed claimed, and the retap was ignored until a restart. A failed `answer()` is now only logged, and any failure before the continuation starts releases the claim; a continuation that started keeps it. Tests: `test/bot/handlers/ai-button-answers.test.ts`.
8. Invitation denials (#909): the denials of `cancel_invitation` and `resend_invitation` (and the shared event-scope denial) lacked `mutationState`, so the executor classed a denied write as `uncertain` and the receipt would ask the user to check the calendar. They now carry `mutationState: 'not_applied'` like `send_invitation`. Tests: `test/services/ai/tool-handlers/sharing-failure-paths.test.ts`.
9. Receipt for a calendar whose owner has no name (#526): the delegated-calendar phrase is "чужой календарь, который ты ведёшь как секретарь" / "someone else’s calendar that you manage as a secretary" only while the requester holds active access; with none (never granted, revoked, expired or an invented id) it is the neutral "другой календарь" / "another calendar", so the receipt never states an access the user lacks (no raw id, no dangling label; a group chat still hides the target). Tests: `test/services/ai/write-receipt.test.ts`.
10. Exact-head review rounds (#909, #526, #920), final behaviour after three rounds; earlier rounds are in git history:
    - `send_invitation` for the owner's calendar answers an event the owner sees only through a group with the scope denial (the secretary can read it anyway), and an event nobody can see (missing, deleted, cancelled) exactly as a missing id; the retry hint for a second managed owner is kept. This supersedes the wording of item 3 for the invisible-event case. A secretary can never invite the calendar owner to their own event (by id or by a username that resolves to the owner).
    - Day and time in the receipt come only from the write itself, never from a read: a create's own request, or the start a successful update restated (an all-day start is parsed with `allDayCalendarDate`, so it is the calendar day written, in any zone; the all-day flag comes from the confirmed result when it carries one, else from the call, and when neither says, the event is named by title alone). Reads supply only the title and the calendar. A delete, a snooze, a failed or unconfirmed update, and an update without a start name the event by title alone. A start names a day or time only if it is a real ISO date, or a datetime with `Z` or an offset (a date-only all-day start is a real ISO date and is shown); anything else names none, in any write. The receipt no longer reads summary dates, read rows or snoozes for a day, which removes the cause of three rounds of fixes (occurrence rows, the first start of a series, a snooze with no data, shifted all-day dates); the summary builder itself (open in #921/#529) still shows the previous day west of UTC and stays open in #921/#529.
    - A create is identified by title, start, all-day flag, owner, scope and recurrence; end, location and description are compared apart. A later success of the same event settles an earlier refused or skipped create whichever of those a corrected retry changed, a later failure is hidden behind a success only when it asked for the same details, and a failure kept visible names the fields it differs in. A refused create that differs from a success of the same title and start only by recurrence or all-day is a different create (those are part of the identity), so it stays visible and its line carries `fields: recurrence` or `fields: all day` to read as a variant, not a contradiction. A successful update re-keys the create to what the event now is (the title and all-day flag from the confirmed result when it carries one) and settles refused creates that asked for exactly that; a delete or a snooze (succeeded or unknown), or an unconfirmed update that may change what the create asked for, retires it, so a failed re-create stays visible. A success after an earlier unknown create leaves the duplicate warning. A repeat of a successful create that ends unknown has its own duplicate warning naming the repeated request; identical failed creates next to a success that asked for other details are told once, and a closing line asks the user to check the calendar, not to repeat, when a possible duplicate and a refusal occur together.
    - An invitee key is the identifier the call named: a user id, or a username read case-insensitively without `@` (the `invitee_username` value `bob`, `@bob` or ` Bob` is one write; a display name is only ever resolved to a username or id by the tool, never used as a key by the ledger). One person's invitation keeps what was delivered and one failure apart (the latest, except that a refusal does not replace an attempt that may have gone through): a failure never erases a delivery, a delivery clears the failure it follows (an unknown one leaves the duplicate warning), and a refusal never erases an attempt that may have gone through. On one receipt line a contact named by username in any case or by id is counted once, and two different people with the same display name are both counted.
    - Tests: `test/services/ai/write-receipt.test.ts` (day and time from the write, create identity, update re-keying, repeat warnings, invitee spellings and slots, `fields:` labels, offsets) and `test/services/ai/tool-handlers/sharing-secretary-invitation-scope.test.ts`.
    - Open, tracked in #922: reminders and `location_abstract` are not compared when deciding whether two creates are the same; a create retired by an unconfirmed update is not re-keyed by a later successful retry; a later success of the same identity is taken for a corrected retry, so a refusal of a genuinely separate second event with the same title and start can disappear; two same-titled events in one receipt are told apart by nothing but their own write's time; one contact named by id and by username is two writes in the ledger (so a delivery by id followed by a refusal by `@name` shows both lines; needs a shared person resolution and the rejection reason class of #910); a long chain of mixed invitation outcomes (a delivery, a created-but-undelivered repeat, then an unknown one) can lose a line; a refused create whose start has no offset and its corrected retry read as two lines; `send_invitation` without `owner_id` on another member's group event answers a plain not found; `update_event` with `all_day: "false"` is stored truthy (the update schema lacks `all_day`); cancel, resend and the roster still call a group event of the owner not found.
