# План внедрения: единый диалоговый движок, справочники и семантика повторений

Дата: 28 сентября 2026. Статус: **план внедрения; ни одна из перечисленных задач этой работой не выполнена**.
Согласуется с [2026-09-28-unified-calendar-dialogue-design.md](../specs/2026-09-28-unified-calendar-dialogue-design.md) (GH-554) и [2026-09-28-recurrence-semantics-583.md](../specs/2026-09-28-recurrence-semantics-583.md) (GH-583). Раздел §17 основного документа задаёт шесть шагов верхнего уровня; этот план разбивает их на атомарные PR-срезы с зависимостями, файлами и критерием RED→GREEN.

## Общие ограничения на весь план
- Текущие обработчики (`add-event.scene.ts`, `workflow-bindings.ts`, `intent-matcher-layer.ts`, `ai-agent-layer.ts`) остаются единственным действующим путём до полной интеграции каждого среза — ни один срез не создаёт второй параллельно активный диалоговый движок. Новый код подключается за feature-флагом и/или юнит-тестами, не за живым трафиком, пока соответствующий срез не пройден целиком.
- Каждый срез — отдельный PR с TDD RED→GREEN (сначала синтетические/юнит-тесты, повторяющие соответствующие declarative cases из `unified-dialogue-contract-cases.jsonl`, затем код).
- Миграции БД — только сохраняющие (см. `CLAUDE.md`), кроме случаев, явно согласованных как destructive с отдельным решением.
- Ни один срез не трогает `#582` (renderer, отдельный владелец) и `#565` (исторический корпус, отдельный владелец) напрямую — только через уже описанные точки интеграции (§28 основного документа).
- Прогонять `bun test`, `tsc`, `bun run lint` на каждом срезе; ни один срез не входит в `main` без прохождения этих проверок и независимого код-ревью (см. `ai-review-before-commit`).

## Срез 1 — Общий парсер времени/неоднозначности и модель all-day (без нового движка)
**Зависимости:** нет (можно начинать сразу).
**Цель:** выровнять `parseWizardDateTime` (`add-event.scene.ts`) и `workflow-bindings.ts::parseTime` на одну общую функцию разбора времени/дня, устранить расхождение голого часа (`2` → `02:00` в мастере vs `INVALID_INPUT` в интенте, §2 основного документа). Ввести общий `Schedule = Timed | AllDay` тип (§8) в существующие типы черновика, не меняя ещё сам диалоговый рантайм.
**Файлы:** `src/services/intent/workflow-bindings.ts`, `src/bot/scenes/add-event.scene.ts`, новый `src/services/event/time-parser.ts` (общая точка), `src/bot/scenes/types.ts` (добавить `all_day`/`participants: []` в `AddEventState`, пока не используемые UI).
**Acceptance (RED→GREEN):** синтетические тесты, повторяющие семейства `time-ambiguous`, `time-explicit`, `time-bare-unambiguous`, `time-invalid`, `all-day` из корпуса — оба потока (`/add`, интент) дают одинаковый результат на одинаковый ввод. Никакого нового UI-поведения пользователю не показывается, если тесты зелёные, а флага ещё нет.
**Откат:** тривиален — общий парсер не подключён к продакшн-маршруту до Среза 2.

## Срез 2 — Typed collect/runtime v3 и адаптеры команда+текст (§21, §25)
**Зависимости:** Срез 1.
**Цель:** ввести версию workflow **v3** (`ParseResult`, `Question`, `DraftPatch`, `transition()` из §5 основного документа) как новый параллельный тип сессии в `WorkflowSessionRepository`, не заменяя v1/v2 на месте. `/add` и все остальные slash-команды начинают принимать полный набор полей операции из аргументов (устраняет пробел `src/bot/commands/add.ts:24-32`, §21), порядок опроса недостающих полей становится адаптивным (§25), а не жёстко «люди сразу после времени».
**Файлы:** новый `src/services/intent/workflow-v3/` (форма `event.create`, `transition`), `src/bot/commands/add.ts` (полный разбор аргументов через общий парсер), `src/database/migrations.ts` (новая таблица/схема-версия для v3-сессий, сохраняющая v1/v2), `src/bot/pipeline/intent-matcher-layer.ts` (маршрутизация v3 за флагом).
**Acceptance:** RED→GREEN на семействах `natural-start`, `number-context`, `people-order`, `negative-entry`, `handoff` корпуса; smoke-тест «/add Встреча завтра в 14:00 с Леной и Антоном в офисе» — все пять полей заполнены одним ходом, нуль LLM-вызовов. Feature-флаг выключен по умолчанию; существующий v1/v2-путь не меняет поведения.
**Откат:** флаг выключается, v3-таблицы остаются неиспользуемыми (не удаляются).

## Срез 3 — Каноничная карточка события и чтение (§26)
**Зависимости:** Срез 1 (не требует Среза 2 — карточка используется и текущими командами).
**Цель:** выделить единый рендерер карточки события (общий для `/today`, `/cal`, `/edit`, подтверждения черновика и ответа на «Покажи сегодняшнюю встречу») из уже существующего форматирования (`src/services/event/formatters.ts`, `worker/templates/event-card.ts`). AI-путь читает события через тот же рендерер, не генерирует карточку прозой.
**Файлы:** `src/services/event/formatters.ts` (выделить `renderCanonicalEventCard`), `src/services/ai/tool-handlers/events.ts` (использовать рендерер вместо текстовой сборки), `src/worker/templates/event-card.ts` (переиспользовать, не дублировать разметку).
**Acceptance:** RED→GREEN на семействе `read-card`; smoke-тест — AI-ответ на «Покажи сегодняшнюю встречу» побайтово совпадает по структуре карточки с ответом `/today` на то же событие; несколько совпадений — picker, не первый результат; ошибка чтения возвращает явный код ошибки, не «пусто».
**Откат:** тривиален, рендерер — чистая функция без побочных эффектов.

## Срез 4 — Контакты: алиасы, коллизии, коллективные группы (§23)
**Зависимости:** Срез 1 (использует общий резолвер identity, но не блокируется Срезом 2/3).
**Цель:** снять `idx_contacts_user_name` уникальность по имени (сохраняющая миграция — переопределить на `(user_id, contact_id)` с отдельным `is_primary_alias`), добавить `contact_aliases`, `contact_groups`, `contact_group_members`; явное подтверждение личности на единственном нечётком совпадении; сохранение подтверждённой коррекции как user-scoped алиаса с обработкой коллизии; команда `/contacts` (add/delete/rename/set-primary для имени и алиасов, список групп и членства).
**Файлы:** `src/database/migrations.ts` (новая сохраняющая миграция), `src/database/repositories/contact.repository.ts` (алиасы/группы), новый `src/bot/commands/contacts.ts`, `src/services/ai/tool-handlers/contacts.ts` (симметричные alias/group actions), переиспользует существующий `ContactRepository.delete` через owner+contactId (закрывает часть #232).
**Acceptance:** RED→GREEN на `alias-confirm`, `contacts-group`, `directory-owner`, `directory-confirmation`, `directory-group`; регресс-тест: два разных контакта с одинаковым именем сосуществуют в одной книге (проверяет снятие старого уникального индекса); точный коллективный алиас приглашает всех без лишнего вопроса, нечёткий — спрашивает.
**Откат:** миграция сохраняющая (данные не теряются); `/contacts` — новая команда, отключаемая без влияния на остальной бот.

## Срез 5 — Места: home/work/household и групповые приглашения (§24)
**Зависимости:** Срез 4 (household привязан к `contact_groups`).
**Цель:** реализовать P2 `#398` (сохранённые места) плюс новые owner-scoped `home`/`work`, contact-linked места и household-связку группы→дом; команда `/places`; интеграция с Срезом 2 — «Настолки у грюковых» при известном точном коллективном алиасе и согласованном доме заполняет title/place/invitees и спрашивает только время.
**Файлы:** `src/database/migrations.ts` (`saved_places`, `place_aliases`, `household_places` — таблицы из §13 основного документа и §24 расширения), `src/services/location/` (новый `SavedPlaceService`, resolver из §10), новый `src/bot/commands/places.ts`, `src/services/ai/tool-handlers/places.ts`.

**Откат:** миграция сохраняющая; `/places` отключаема независимо от остального.

**Зависимости:** независим от Срезов 2–6 (может идти параллельно после Среза 1); желательно до полного включения Среза 2 для всех сценариев, где `event.create` поддерживает recurrence.
**Цель:** реализовать §2–§10 `2026-09-28-recurrence-semantics-583.md` — единый `parseRecurrenceBlock()`, отклонение множественного `RRULE`/`EXRULE`, честная поддержка `EXDATE`/`RDATE` в `expandRecurrence()`, точная instant-идентичность исключения (с миграцией/флагом unresolved для legacy-записей), исправление двойного префикса в `ics/generator.ts`, чтение `EXDATE`/`RDATE` в `ics/parser.ts`, unique-индекс на `event_reminders(event_id, remind_at_utc)`, операции «одно/все/это и будущие» с явным consent/CAS/идемпотентностью.

## Владение и трекинг
Каждый срез — отдельная evidenced-задача в task-cli, дочерняя по отношению к #554 (Срезы 1–6, 8) или #583 (Срез 7), с явным acceptance criteria из соответствующего пункта выше. Срез 6 явно ссылается на #257/#565/#566 как совладельцев контракта качества, не дублирует их работу. Ни один срез не начинается до согласования владельцем письменной спецификации (§1 основного документа: «Сначала согласовать эту спецификацию»).
