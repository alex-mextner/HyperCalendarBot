## 1. Как это устроено сейчас — аудит с воспроизведением, не предположение

Ниже — наблюдения на чистых синтетических данных через реальную функцию `expandRecurrence()` и логику `generateIcs()`, без обращения к БД, сети или чужим данным. Скрипт-проба хранится как одноразовый артефакт этой сессии (не коммитится в репозиторий; вывод приведён построчно).

### 1.1 Хранение: два несовместимых формата `recurrence_rule` в одном столбце
- Локально созданное событие (`/add`, AI tool `create_event`) хранит **голое** тело правила без префикса `RRULE:`, например `"FREQ=WEEKLY;INTERVAL=1;COUNT=6"` — так его описывает схема AI-инструмента (`src/services/ai/tools.ts:107`: *«RRULE for recurring events, e.g. "FREQ=WEEKLY;INTERVAL=2"»*) и так его пишут `src/services/ai/tool-handlers/events.ts:389` и `src/bot/scenes/add-event.scene.ts:474` — оба просто передают `recurrence_rule` дальше без нормализации.
- Синхронизированное из Google событие хранит **многострочный** блок с префиксами: `src/services/google/event-mapper.ts:101` при экспорте в Google делает `event.recurrence = local.recurrence_rule.split('\n')`, а при импорте (`event-mapper.ts:134`) — `recurrence_rule: gEvent.recurrence.join('\n')`, то есть само значение Google API `recurrence: string[]` (обычно `["RRULE:...", "EXDATE:...", "RDATE:..."]`) склеивается через `\n` без изменений.
- Импорт `.ics`: `src/services/ics/parser.ts:64-66` кладёт в `recurrence_rule` содержимое ровно одной строки `RRULE:` (`case 'RRULE': current.recurrence_rule = value` — `value` уже без префикса `RRULE:`, т.к. префикс отрезан на этапе разбора `key:value`), а `EXDATE`/`RDATE` строки парсер вообще не обрабатывает (`unfoldIcsLines`/цикл разбора не содержит `case 'EXDATE'`/`case 'RDATE'`) — при импорте `.ics` с исключениями они молча теряются на входе, до всякого экспандера.

Три источника пишут в один столбец три разных по форме и по полноте значения. Ни один текущий читатель (`expandRecurrence`, `formatRecurrenceHuman`, `generateIcs`, `setRecurrenceUntil`) не унифицирует эти формы — каждый угадывает по наличию префикса `RRULE:`.

### 1.2 `expandRecurrence()` полностью игнорирует `EXDATE`/`RDATE` — подтверждено пробой
`src/services/event/recurrence.ts:27-34`:
```ts
const rruleLine =
  template.recurrence_rule.split('\n').find((line) => line.startsWith('RRULE:')) ?? template.recurrence_rule;
const rruleString = `DTSTART:${formatRRuleDate(dtstart)}\n${rruleLine}`;
const rule = rrulestr(rruleString);
```
Берётся **только** строка `RRULE:`; если исходное значение содержит `EXDATE:`/`RDATE:` (случай Google-синка из §1.1), эти строки просто выбрасываются до вызова `rrulestr`, который их никогда не видит.

Проба (fixture: `DTSTART=2026-01-06T10:00Z`, `RRULE:FREQ=WEEKLY;INTERVAL=1;COUNT=6\nEXDATE:20260113T100000Z\nRDATE:20260301T100000Z`, диапазон `2026-01-01..2026-03-05`):
```
occurrence count: 6
[ 2026-01-06, 2026-01-13, 2026-01-20, 2026-01-27, 2026-02-03, 2026-02-10 ]
```
Ожидание по данным: 5 еженедельных вхождений минус `2026-01-13` (EXDATE) плюс одно добавленное `2026-03-01` (RDATE) = 6 дат, но **другой набор дат** — `2026-01-13` обязано отсутствовать, `2026-03-01` обязано присутствовать. Фактически получены все 6 еженедельных дат без исключения и без добавленной — `EXDATE`/`RDATE` не оказывают на результат никакого эффекта. Это прямое, воспроизведённое на реальном коде подтверждение формулировки #583 «current expander selects one RRULE line and can omit RDATE or EXDATE».

Важно: библиотека `rrule` это умеет из коробки — `rrulestr()` данная **полным** многострочным блоком (`DTSTART:...\nRRULE:...\nEXDATE:...\nRDATE:...`) возвращает `RRuleSet`, чей `.between()` уже комбинирует `RRULE`/`RDATE`/`EXRULE`/`EXDATE` корректно (см. пример в README rrule.js: `rrulestr('DTSTART:...\nRRULE:FREQ=MONTHLY;COUNT=5\nRDATE:...\nEXRULE:...\nEXDATE:...')`). Пробел — в том, что наш код обрезает вход до вызова библиотеки, а не в том, что библиотека не поддерживает такой набор.

### 1.3 Идентичность исключения — календарная дата, а не точный исходный instant
`src/services/event/recurrence.ts:51-61,79-80`: при `adjustDst` (обычное таймд-событие со своей таймзоной) ключ соответствия исключения — `toLocalDateKey(exc.original_start_at, template.timezone)`, то есть **календарная дата** в локальной таймзоне шаблона, а не точный zoned instant. Комментарий в коде объясняет мотив («handles both old exceptions... and new ones»), но follow-up: если правило когда-либо порождает более одного вхождения в один и тот же локальный календарный день (составное правило вида «несколько раз в день», сдвинутое через RDATE вхождение в тот же день, что и обычное, или граница смены дня при DST), `exceptionMap` — обычный `Map`, и второе вхождение с тем же ключом даты **перезапишет** первое при построении карты (строка 59: `exceptionMap.set(key, exc)`), либо оба совпадающих occurrence сматчатся на одно и то же exception-событие. Это ровно тот пробел, который #583 требует закрыть явно («exception identity=original exact start not calendar day»): текущий код такой identity не предоставляет для таймд-серий — только для all-day (`adjustDst=false` ⇒ ключ `new Date(exc.original_start_at).toISOString()`, точный UTC-instant, но пока в проекте нет пути создать несколько all-day исключений в один день по конструкции).

### 1.4 ICS-экспорт: двойной префикс на Google-синхронизированных сериях
`src/services/ics/generator.ts:26`:
```ts
if (event.recurrence_rule) lines.push(`RRULE:${event.recurrence_rule}`);
```
Для локально созданного события (`recurrence_rule` без префикса) это корректно: `RRULE:FREQ=WEEKLY;INTERVAL=1;COUNT=6`. Для Google-синхронизированного события (`recurrence_rule` уже содержит `"RRULE:FREQ=...\nEXDATE:...\nRDATE:..."`, §1.1) результат — **`RRULE:RRULE:FREQ=WEEKLY;...`** с задвоенным префиксом на первой строке, подтверждено инлайн-пробой той же строки кода на фикстуре из §1.2:
```
RRULE:RRULE:FREQ=WEEKLY;INTERVAL=1;COUNT=6
EXDATE:20260113T100000Z
RDATE:20260301T100000Z
```
Такой `.ics` синтаксически некорректен (`RRULE:RRULE:...` не парсится ни одним валидным ICS-парсером, включая наш собственный — `src/services/ics/parser.ts:64` требует точное совпадение `case 'RRULE'` по имени свойства до `:`, а не по префиксу значения). `/export` пока не подключён (`src/services/ics/generator.ts:1-2`: «Not currently wired up — /export command has not been implemented yet»), поэтому это не действующий production-баг, а дефект, который проявится сразу при подключении `/export`, если формат `recurrence_rule` не унифицировать раньше.

### 1.5 `setRecurrenceUntil` — единственное корректное место
`src/database/repositories/event.repository.ts:612-633` при перезаписи `UNTIL` явно разделяет строки на `RRULE:`-строку и «остальные» (`otherLines`), меняет только `UNTIL=` внутри RRULE-тела и **сохраняет** `otherLines` (в т.ч. `EXDATE`/`RDATE`) при пересборке. Это правильный образец многострочной обработки — остальным читателям (`expandRecurrence`, `generateIcs`, `formatRecurrenceHuman`) стоит следовать тому же паттерну «разделить по строкам → трогать нужную → пересобрать всё», а не читать/писать одну строку.

### 1.6 Напоминания: реконсиляция и идемпотентность
`src/services/notification/materializer.ts:205-243` (`materializeUpcomingRecurringReminders`) вызывает `expandRecurrence()` для каждого шаблона на скользящее окно и для каждого occurrence — `materializeForOccurrence()`, который **не удаляет** существующие напоминания, а вставляет только недостающие: перед каждым `insert()` вызывается `EventReminderRepository.existsForEventAt(eventId, remindAtUtc)` (`src/database/repositories/event-reminder.repository.ts:59-62`, `SELECT 1 FROM event_reminders WHERE event_id = ? AND remind_at_utc = ?`). Это **прикладная** проверка-затем-вставка, не атомарная операция БД: в таблице `event_reminders` (`src/database/migrations.ts:166-182`) нет `UNIQUE(event_id, remind_at_utc)` — только обычные индексы `idx_event_reminders_due`/`idx_event_reminders_event`. Дедупликация верна при последовательном выполнении (один worker-тик за раз, как сейчас через BullMQ), но не защищена на уровне схемы от повторной вставки при параллельном запуске двух materializer-проходов. Поскольку `expandRecurrence()` сейчас не учитывает `EXDATE`/`RDATE` (§1.2), отменённые через Google/ICS вхождения серии сегодня **получают** напоминания, которых быть не должно — прямое следствие бага §1.2, не отдельная проблема реконсиляции.
Отменённое исключение (`is_exception && event.is_cancelled`) корректно пропускается в цикле материализации (`materializer.ts:224`), это уже правильно реализовано для explicit exception-строк (не для `EXDATE`).

### 1.7 `BYHOUR` с несколькими значениями — второе вхождение того же дня схлопывается в первое (независимо подтверждено этой сессией)
Тот же дефект §1.2 (усечение входа до вызова `rrulestr()`) имеет ещё одно наблюдаемое следствие, независимо подтверждённое здесь синтетической пробой против реальной `expandRecurrence()` (не копия, тот же импорт), помимо уже опубликованного на #583 в 17:00 UTC read-only замера этой же сессии на `d94e34916b804ea2e15af065da5e63c3c1f3a563`:
```
template.recurrence_rule = 'FREQ=DAILY;COUNT=2;BYHOUR=10,14', DTSTART=2026-10-01T10:00:00.000Z
expandRecurrence(template, [], '2026-09-30T00:00Z', '2026-10-05T00:00Z')
→ occurrence count: 2
→ [ '2026-10-01T10:00:00.000Z', '2026-10-01T10:00:00.000Z' ]
```
Ожидание по RFC 5545 §3.3.10 (`BYHOUR` расширяет каждый день правила на список часов): два разных вхождения одного дня, `10:00` и `14:00`. Фактически оба вхождения возвращаются с идентичным `occurrence_start` — `14:00` не появляется вовсе, `10:00` дублируется. Это тот же класс дефекта, что и §1.2 (усечённый `rruleLine`, теряющий часть семантики правила до передачи в `rrulestr()`), и напрямую подтверждает нужду в идентичности напоминания по `(event_id, user_id, occurrence_start, interval_minutes)`, а не по `remind_at_utc` (§7) — потому что даже после исправления самого экспандера два РАЗНЫХ вхождения одного дня остаются двумя разными строками `occurrence_start`, которые могут (через разные настроенные интервалы) материализовать напоминания на один и тот же `remind_at_utc`.

## 2. Поддерживаемый набор RRULE + RDATE/EXDATE — целевая семантика

**Одно правило `RRULE` на серию.** RFC 5545 Appendix A.1.2: *«The "RRULE" property SHOULD NOT occur more than once in a component»* — множественный `RRULE` в одном `VEVENT` синтаксически не запрещён на уровне грамматики (`rrule` — часть `*(...)`, повторяемая группа `eventprop`), но его семантика с несколькими экземплярами не определена стандартом. Наш движок явно **отклоняет** (валидационная ошибка при сохранении, не выполняет «взять первое и промолчать») более одной строки `RRULE:` в одном `recurrence_rule`, и явно отклоняет `EXRULE` — RFC 5545 Appendix A.3.1: *«The "EXRULE" property can no longer be specified in a component»* (устарело ещё в переходе с RFC 2445), incoming `.ics`/Google данные с `EXRULE` помечаются как неподдерживаемые и сохраняются как read-only «правило с нераспознанным свойством», не как молчаливо отброшенное или молчаливо применённое правило.
**RDATE/EXDATE — множественные, многострочные.** Каждое свойство `EXDATE`/`RDATE` может повторяться (RFC 5545 §3.8.5.1–3.8.5.2, `eventprop`: `exdate`/`rdate` — «MAY occur more than once»), и одна строка может содержать список дат через запятую. Движок хранит полный многострочный блок `RRULE:...\nEXDATE:...\nRDATE:...` (несколько `EXDATE`/`RDATE` строк допустимы) и передаёт его **целиком** в `rrulestr()` (не выборочно, устраняя §1.2) с включённым `forceset`, чтобы результатом всегда был `RRuleSet`, а не одиночный `RRule`. `DTSTART` собирается из `start_at` шаблона отдельно, синхронно с правилом (RFC 5545 A.1.1: *«The DTSTART property SHOULD be synchronized with the recurrence rule»*) — сохраняется уже верный шаблон из текущего кода (§1, `formatRRuleDate`).
**DATE vs DATE-TIME согласованность.** Значения `EXDATE`/`RDATE` обязаны совпадать по типу значения с `DTSTART` серии (RFC 5545 §3.8.5.1/3.8.5.2: value type EXDATE/RDATE наследуется от DTSTART, если не переопределён параметром `VALUE=`). All-day серия (`DTSTART;VALUE=DATE`) допускает только `EXDATE`/`RDATE` со значением-датой (`YYYYMMDD`), не `DATE-TIME`; смешение типов — явная ошибка валидации при сохранении правила, не молчаливое приведение.
**COUNT и UNTIL взаимоисключающи** (уже зафиксировано в дизайне §14: «COUNT и UNTIL одновременно не задаются») — сохраняется как обязательная проверка на этапе сохранения правила, не только текстовая рекомендация в подсказке.
**Множественная композиция по дням недели/интервалу/n-й день месяца** — переиспользуется уже существующая интеграция `rrule` (`BYDAY`, `INTERVAL`, `BYSETPOS`/n-й день недели через `RRule` API), первая расширенная группа ограничена перечисленным в §14 дизайн-документа (несколько дней недели, интервал недель, n-й/последний день недели месяца, `COUNT`/`UNTIL`, явные `EXDATE`). «Каждый последний рабочий день месяца» и перенос с праздников остаются нерешённым условием (§14) — этот документ не расширяет поддержанный набор дальше уже согласованного.

## 3. DTSTART, таймзоны и DST

Единая точка правды для локального времени серии — `start_at` (UTC instant) + `timezone` (IANA) шаблона; библиотека `rrule` разворачивается в чистом UTC (уже так в `recurrence.ts`), а перевод каждого сгенерированного instant в правильный локальный час выполняет `adjustOccurrenceForDst()` через `TZDate`, беря локальные `H:M:S` из `dtstart` и применяя их заново для каждой даты — сохраняется существующий, уже корректный для однозначных случаев подход. Диапазон разворачивания паддится на `±3` часа (`DST_PAD_MS`) для вхождений, «переезжающих» через границу диапазона после DST-коррекции, затем пост-фильтруется — сохраняется как есть.
**Весенний пропуск (spring-forward gap).** Локальное время, которого не существует в этот день (например `02:30` в день перехода, когда `02:00→03:00` пропускается) — движок обязан вернуть явную причину `nonexistent_local_time` для этого occurrence вместо тихого сдвига на час вперёд или назад; вызывающий код (preview/подтверждение) обязан предложить выбор другого времени для этого конкретного вхождения, не менять правило целиком.
**Осенний повтор (fall-back repeat).** Локальное время, повторяющееся дважды (например `02:30` дважды в день перехода назад) — движок возвращает оба кандидата instant с UTC-offset у каждого («первое/второе вхождение» уже сформулировано в §14 дизайн-документа) и требует явного выбора для этого occurrence при первом столкновении; после выбора конкретный instant фиксируется как exception (§4), не пересчитывается на каждый показ.
**Нет глобального правила «всегда летнее» или «всегда зимнее»** (уже в §14) — реализация обязана давать разные ответы на весенний и осенний случай, не единую эвристику.

## 4. All-day и cross-midnight

All-day серия хранит `StartDate`/`EndDateExclusive` как календарные даты без таймзоны экспандера (§8 дизайн-документа: `AllDay{startDate, endDateExclusive, timezone}` — `timezone` здесь для отображения/напоминаний, не для сдвига самой даты). `EXDATE`/`RDATE` для all-day серии обязаны быть `VALUE=DATE`, сравниваются и хранятся как календарные даты, не как UTC-instant — календарная арифметика (прибавление/вычитание суток в конкретной таймзоне), не `+86400000` мс, поскольку сутки в конкретный день при переходе DST не равны 86 400 000 мс в UTC.
Cross-midnight timed-событие (например `23:00–01:30` следующего дня) — `occurrence_end` уже вычисляется через `durationMs` от скорректированного `occurrence_start` (текущий код `recurrence.ts:96`, `new Date(utcDate.getTime() + durationMs)`), что корректно для фиксированной длительности; экспандер обязан явно поддерживать диапазон запроса, пересекающий полночь — occurrence, начавшийся до полуночи запрошенного дня и завершившийся после, должен попадать в выдачу для обоих затронутых календарных дней там, где вызывающий код (agenda/картинка недели) группирует по дню.

## 5. Исключения: изменённые, отменённые, перенесённые внутрь/наружу диапазона

**Идентичность исключения = точный исходный instant серии** (`(templateId, originalStartInstant, valueKind)`, `valueKind` = `date` для all-day, `date-time` для timed), не календарная дата — целевая семантика, закрывающая §1.3. Для timed-серии это **разрешённый** (resolved) instant после DST-коррекции — то есть значение `utcDate`/`occStart` в терминах текущего кода (`recurrence.ts:75-78`, после `adjustOccurrenceForDst()`), а не сырая дата, которую отдаёт `rule.between()` до этой коррекции: сырая pre-adjustment дата — вспомогательная величина итератора `rrule`, не реальное время начала вхождения, и не совпадает с тем, что хранится в `exc.original_start_at` или с Google `originalStartTime` (см. ниже) — использовать её как ключ идентичности означало бы, что DST-исключения и round-trip с Google-инстансами адресуют разные вхождения. Именно это разрешённое значение фиксируется один раз в момент первого превращения occurrence в exception и переносится в `original_start_at` **без изменений** при последующих переносах вхождения (`start_at` меняется, `original_start_at` — нет; это уже так в текущей модели, `event.repository.ts:562-585`). Two occurrences с разным точным instant, но одинаковой локальной календарной датой, обязаны иметь разные ключи exception — это прямое требование #583; реализация обязана заменить `Map<localDateKey, exc>` на ключ по точному разрешённому instant (плюс `valueKind`). **Устаревшие записи без сохранённого точного instant не получают молчаливый date-match фолбэк**: миграция обязана попытаться восстановить точный instant для каждой такой записи по существующим данным (пересчитать разрешённое вхождение шаблона на эту календарную дату); если на эту дату у серии ровно одно вхождение — восстановление однозначно, запись мигрирует на точный instant автоматически. Если на эту дату приходится несколько вхождений (коллизия, тот же риск, что и для новых записей) — однозначного восстановления нет, запись помечается `identity_unresolved` и требует ручного разрешения администратором/владельцем данных перед тем, как снова участвовать в сопоставлении экспандера; она не сопоставляется автоматически ни с одним из кандидатов, чтобы не выбрать не то вхождение.
**Модифицированное вхождение** — строка в `events` с `parent_event_id` + `original_start_at` (уже существующая модель, `event.repository.ts:562-596`), `start_at`/другие поля отличаются от того, что дал бы шаблон; отображается как обычное событие с признаком «изменённое вхождение серии».
**Отменённое вхождение** — та же exception-строка с `is_cancelled=1`; уже корректно пропускается и в развёртке (`recurrence.ts:83-85`), и в материализации напоминаний (`materializer.ts:224`). Обязательное дополнение: то же самое отменённое вхождение должно попадать и в `EXDATE` при экспорте в Google/ICS, а не оставаться видимым только внутри локальной модели.
**Перенос вхождения ВНУТРЬ запрошенного диапазона** (`original_start_at` вне диапазона, `start_at` внутри) — occurrence обязан появиться в выдаче под новым `start_at`, экспандер обязан отдельно разворачивать exception-строки по их **текущему**, а не исходному времени, когда фильтрует по диапазону.
**Перенос вхождения НАРУЖУ диапазона** (обратный случай) — occurrence обязан **исчезнуть** из выдачи текущего диапазона (не остаться на месте шаблонной даты — иначе пользователь увидит вхождение дважды: на старом месте как «незамеченное исключение» и на новом).
**Round-trip идентичности между Google и локальной моделью.** Google представляет исключение через отдельный instance-ресурс с `recurringEventId` + `originalStartTime` (см. [Access instances / Modify or delete instances](https://developers.google.com/workspace/calendar/api/guides/recurringevents)); `originalStartTime` — это именно точный исходный instant по правилу родителя, «uniquely identifies the instance within the recurring event series even if the instance was moved» — прямое текстовое подтверждение Google API, что identity обязана быть точным instant, а не календарной датой, что совпадает с целевой семантикой этого документа и с формулировкой #583.

## 6. Редактирование: одно / все / это и будущие

Переиспользуется существующая инфраструктура: `getExceptionsFrom`/`reparentExceptions`/`deleteExceptionsFrom`/`setRecurrenceUntil` (`event.repository.ts:590-633`) уже реализуют паттерн «это и будущие» — закрыть старую серию через `UNTIL` перед точкой разреза, создать новый шаблон с исключениями, перенесёнными через `reparentExceptions`. Это верная основа; документ фиксирует контракт поверх неё:
- **«Только это вхождение»** — создать/обновить exception-строку с `original_start_at` = точный instant (§5); не создаёт нового шаблона, не трогает `UNTIL`.
- **«Все вхождения»** — редактирует сам шаблон (`recurrence_rule`, `start_at` и т.д.); существующие exception-строки, у которых изменённое поле явно переопределено (например у exception своя своя `start_at`, не унаследованная), не откатываются автоматически — тот же принцип «уже введённые независимые данные не сбрасываются», что уже в §5 основного дизайна для черновика.
- **«Это и будущие»** — `setRecurrenceUntil` на старом шаблоне + новый шаблон с `dtstart` = точка разреза + `reparentExceptions`/`deleteExceptionsFrom` в зависимости от того, сохраняются ли будущие исключения в новой серии или относятся к старому правилу. Все три пути используют одинаковые `entityRevision` CAS, idempotency key и effect ledger, что уже зафиксировано в §15/§20 основного дизайн-документа для commit одиночного события — этот документ не создаёт параллельный механизм подтверждения.

## 7. Уведомления участников и напоминания

Изменение «все вхождения» или «это и будущие» затрагивает уведомления так же, как редактирование обычного события (существующий `InvitationService`/`participant-change-handler.ts`) — приглашённые на серию получают уведомление об изменении, приглашённые только на конкретное отменённое/изменённое вхождение — уведомление именно об этом вхождении, не обо всей серии. Реконсиляция напоминаний (§1.6) обязана после устранения §1.2 естественно перестать материализовать напоминания для `EXDATE`-исключённых дат — отдельного нового кода для этого не нужно, expandRecurrence уже не вернёт такие occurrence.
**Идентичность на уровне схемы — исправлено после ревью #554 17:22 UTC.** Предыдущая формулировка ошибочно рекомендовала `UNIQUE(event_id, remind_at_utc)` — этот ключ коллидирует между разными получателями (`user_id`) одного события/вхождения, и между разными вхождениями серии, чьи вычисленные `remind_at_utc` случайно совпадают (см. `recurrence-reminder-reconciliation-005` в корпусе: вхождение в 14:00 с настроенным интервалом «за 4 часа» и вхождение в 10:00 того же дня с интервалом «в момент начала» оба материализуются в 10:00Z — это не редкий край, а прямое следствие уже подтверждённого §1's BYHOUR-бага «10:00 дважды, 14:00 схлопывается», исправление которого сделает оба вхождения обычными, с собственными независимыми напоминаниями). Реальная схема `event_reminders` (`src/database/migrations.ts:166-177`, дополнена в `046_occurrence_start_end_and_rematerialize:887-888`) уже содержит нужные для идентичности столбцы: `event_id`, `user_id` (получатель), `occurrence_start` (канонический ключ конкретного вхождения — тот же resolved instant, что и идентичность исключения в §5, не сырая `remind_at_utc`), `interval_minutes` (какое именно настроенное напоминание — «за 30 минут», «в момент начала» и т.д., all-day использует сентинел `-1` с `interval_label`). Целевая уникальность — **`UNIQUE(event_id, user_id, occurrence_start, interval_minutes)`**, не `remind_at_utc`: `remind_at_utc` — производное поле (`occurrence_start − interval_minutes`), пригодное для `idx_event_reminders_due`, но не для identity, потому что разные комбинации `(occurrence_start, interval_minutes)` могут дать одно и то же итоговое UTC-время. Столбца `channel` в `event_reminders` сегодня нет — доставка идёт только Telegram, канал как отдельное измерение транспорта живёт в `notification_log` (`channel TEXT NOT NULL DEFAULT 'telegram_text'`), а не в `event_reminders`; если появится второй канал доставки напоминаний, `channel` войдёт в ключ отдельной сохраняющей миграцией — эта спецификация не придумывает колонку, которой нет, и не проектирует наперёд непоявившееся требование.
**Найденный сопутствующий баг в текущем коде.** `EventReminderRepository.existsForEventAt(eventId, remindAtUtc)` (`src/database/repositories/event-reminder.repository.ts:59-64`) фильтрует только по `event_id` и `remind_at_utc` — **не по `user_id`**, то есть при нескольких получателях одного события/вхождения с совпадающим `remind_at_utc` уже сегодня прикладная de-dup-проверка теоретически может заблокировать вставку строки второго получателя, приняв её за дубликат первого (см. `recurrence-reminder-reconciliation-004`). Это существующий баг применения, а не довод в пользу того, чтобы официально закрепить `(event_id, remind_at_utc)` как правильный уникальный индекс — наоборот, он ещё раз показывает, что этот ключ не идентифицирует строку однозначно. Исправление `existsForEventAt` на `(event_id, user_id, occurrence_start, interval_minutes)` и добавление того же кортежа как БД-уровневого `UNIQUE INDEX` — часть одной миграции, не двух независимых решений. Для не-периодических событий (`materialize()`, не `materializeForOccurrence()`) сегодня `occurrence_start` не заполняется (`NULL`) — миграция обязана сначала backfill'ить `occurrence_start = events.start_at` для существующих строк одиночных событий, иначе `UNIQUE`-индекс с `NULL` в SQLite не дедуплицирует их вовсе (SQLite не считает `NULL = NULL` для уникальности). Существующие дубликаты (если найдутся) не удаляются молча — миграция сначала проверяет их отсутствие/помечает конфликт, как уже написано в §1.6/предыдущей формулировке; удаление без явного решения не выполняется.

## 8. Google и ICS round-trip

**Google.** `localToGoogle`/`googleToLocal` (`event-mapper.ts`) уже перекладывают массив `recurrence: string[]` в `recurrence_rule` через `join('\n')`/`split('\n')` без потери строк — сохранение формата корректно на уровне транспорта; провал в §1.1–1.2 — в том, что **читатели** внутри нашей системы (`expandRecurrence`, `generateIcs`) не читают многострочный блок целиком. Целевое исправление (не в этом документе — отдельная реализация) — унифицировать хранение: `recurrence_rule` всегда хранит канонический многострочный блок с явным префиксом `RRULE:` на первой строке (мигрировать локально создаваемые голые правила на префиксную форму при записи), и все читатели работают с полным блоком через один общий `parseRecurrenceBlock()`/`rrulestr(..., {forceset:true})`, а не через `.find(line => line.startsWith('RRULE:'))`.
**ICS.** Тот же общий `parseRecurrenceBlock()` для экспорта устраняет двойной префикс §1.4 (сериализовать `RRULE:`/`EXDATE:`/`RDATE:` построчно из структурированного представления, не конкатенацией строк). Импорт `.ics` (`ics/parser.ts`) обязан читать `EXDATE`/`RDATE` строки (сейчас отсутствуют в switch — §1.1) и сохранять их в тот же канонический блок, не отбрасывать.
**Round-trip проверка.** Экспорт в Google → повторный импорт того же события (или экспорт в `.ics` → импорт обратно) обязаны воспроизводить тот же набор вхождений и исключений в пределах разворачиваемого горизонта — это future RED-тест (не результат этой спецификации), закрывающий acceptance criterion #583 «Google and ICS round-trip preserves recurrence meaning».

## 9. Ограничения развёртки и explicit unsupported

Переиспользуются уже согласованные защитные лимиты §14 основного документа: preview — 5 дат, полная развёртка — по явному диапазону с ограничением числа вхождений и CPU-времени, без материализации бесконечной серии целиком и без выполнения произвольного кода в условии повторения. Явно **не поддерживается** и отклоняется с понятной причиной, а не молча упрощается:
- более одной строки `RRULE:` на серию (§2, RFC 5545 A.1.2);
- `EXRULE` (устарело в RFC 5545 A.3.1, но встречается в старых `.ics`/легаси-данных);
- смешение `VALUE=DATE` и `VALUE=DATE-TIME` между `DTSTART` и `EXDATE`/`RDATE` одной серии;
- `RRULE` без `DTSTART` в серии, где восстановить `DTSTART` из другого источника невозможно;
- горизонт развёртки за пределами согласованного лимита (бесконечный `COUNT`/`UNTIL` в отдалённом будущем без явного диапазона запроса).

## 10. Миграция, обратная совместимость и откат

Изменение формата хранения `recurrence_rule` (унификация на канонический многострочный префиксный блок, §8) — **сохраняющая** миграция: существующие голые правила читаются как раньше через фолбэк (`.find(...) ?? весь_текст`, уже в текущем коде) и при следующей записи приводятся к канонической форме; массового backfill всех исторических строк в один проход эта спецификация не предполагает без отдельного явного решения о destructive/preserving миграции (см. `CLAUDE.md`: «Always ask whether to run a destructive migration ... or a preserving migration»). Замена ключа идентичности исключения (§5, инстант вместо календарной даты) обязана попытаться восстановить точный instant для каждой существующей exception-записи без него и мигрировать её автоматически там, где восстановление однозначно (ровно одно вхождение шаблона на эту календарную дату); там, где однозначного восстановления нет (несколько вхождений на ту же дату), запись помечается `identity_unresolved` для ручного разрешения — не переинтерпретируется задним числом как «неправильная» и не сопоставляется молча ни с одним из кандидатов.
Откат к текущему поведению — фича-флаг на новый `parseRecurrenceBlock()`/новую идентичность исключения; старый путь (`.find(line => line.startsWith('RRULE:'))`, дата-ключ) остаётся доступным до полного прохождения RED→GREEN тестов на реальных исторических сериях.
**Откат не должен молча реинтерпретировать уже принятые данные — уточнение после ревью #554 17:22 UTC.** Флаг выключается не только до включения, а потенциально и **после** того, как под новым движком уже были сохранены/приняты серии с настоящими `EXDATE`/`RDATE` (например, серия, для которой пользователь явно исключил дату через новый UI, или Google-синк с реальным многострочным блоком). Простое «флаг выключен → зовём старый путь» для такой серии означало бы, что старый усечённый парсер (`.find(line => line.startsWith('RRULE:'))`) снова молча отбросит `EXDATE`/`RDATE` — это ровно баг §1.2/§1.4, который эта спецификация исправляет, только теперь воспроизведённый через сам механизм отката, а не через отсутствие фичи. Требование: откат обязан быть **capability/version-gated по конкретной серии**, не глобальным rewind чтения для всех записей —
- серия, у которой `recurrence_rule` не содержит `EXDATE`/`RDATE` (обычный однострочный `RRULE`) — при выключенном флаге читается старым путём без изменений, результат идентичен текущему production (`recurrence-rollback-001` в корпусе);
- серия, у которой `recurrence_rule` содержит `EXDATE`/`RDATE` (уже сохранённые под новым движком или из Google-синка) — при выключенном флаге **не подаётся** в старый усечённый парсер: развёртка обязана либо продолжить использовать read-only путь нового `parseRecurrenceBlock()` для чтения (чтение — не запись, откат ограничивает только приём новых данных/UI, не корректность уже показываемых), либо, если это тоже недоступно (флаг полностью отключает и чтение), вернуть явный `recurrence_display_unsupported_disabled` результат вызывающему коду вместо молчаливо неполного набора вхождений (`recurrence-rollback-002` в корпусе). Молчаливая потеря `EXDATE`/`RDATE` через откат — то же самое поведение, которое эта спецификация называет багом в §1.2, вне зависимости от того, вызвана она отсутствием фичи или откатом уже включённой.
- запись данных (`EXDATE`/`RDATE` от пользователя) при выключенном флаге не принимается новым UI — это уже покрыто feature-флагом на уровне ввода; раздел выше — про уже существующие в БД серии, накопленные до отключения флага.
Никакие production-записи, миграции с потерей данных или живые Google/ICS синки этой работой не выполнялись и не планируются к выполнению в рамках написания документа — только чтение кода и синтетические read-only пробы (§1).
