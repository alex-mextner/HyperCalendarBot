# Единая обвязка качества: пресеты, Laya, контекст, проверки и повторное исправление

**Статус: проект спецификации; не реализованный production-маршрут.** 28 сентября 2026, Europe/Belgrade.
База проверенного кода: `7399876eeb572e0c021cb44004931aec80624311`. Эпик #219; исполнение #257, контекст #226, replay #565, общий policy layer #566. Benchmark PR #429 — источник предварительных измерений, не конечный критерий безопасности.

## 1. Цель и граница ответственности

Подбирается не одна «самая умная модель», а система **пресет → классификация → достаточный контекст → план → безопасное исполнение → доказательный ответ → проверка/исправление**. Требуемый результат — быстрое правильное поведение на всём доступном историческом корпусе, а не высокий балл отдельных LLM на упрощённом стенде.

Цель релиза: 100% task-correct исходов на полной независимо размеченной и воспроизводимой части исторического лога, ноль неправильных записей и ноль недоказанных утверждений об исполнении. Невосстановимые эпизоды, пропуски источников и нерешённые случаи публикуются отдельно; они не исчезают из отчёта о покрытии. Уточнение считается успехом только там, где оно действительно требуется. Ответ «не знаю» на каждый вопрос не позволяет выполнить цель.

Рядом всегда публикуется coverage: какая доля всех найденных исходных эпизодов восстановлена и оценена. Если coverage меньше100%, нельзя писать «100% на всём историческом логе», даже если все оценённые эпизоды прошли.

Это проверяемая цель для зафиксированного корпуса, не обещание математической безошибочности на любом будущем сообщении. Система сохраняет безопасную остановку, проверку фактов и обновляемую регрессионную базу. Cosmetic exact-match не приравнивается к корректности действия.

## 3. Пресеты и решения по моделям

Один `ModelPreset` имеет версионированные поля: `id`, `role`, `provider`, `model`, `effort`, `temperature`, `output_budget`, `request_deadline`, `supported_protocols`, `privacy_class`, `entitlement_ref`, `qualification_ref`, `status`. `effort` — отдельное измерение, не подстрока имени модели. Неподдерживаемая настройка не заменяется молча. Сохранение provider-specific полей между tool rounds входит в адаптер и тесты.

| Роль | Решение для следующей интеграции | Ограничение |
|---|---|---|
| `route_semantics` | Laya multilingual как предпочтительный локальный обучаемый классификатор; сначала shadow | Первые измерения не позволяют доверять ей как единственному маршрутизатору |
| `context_plan` | Кандидат Gemini2.5Flash-none, затем проверенный GLMFlash-low | Возвращает только типизированный план чтений и схем; не исполняет business write |
| `execute_standard` | Основные кандидаты GLM5.3Flash-low и DeepSeekV4.1Flash | Порядок по реальным API-правам, цене, задержке и общему replay; ни один пока не сертифицирован |
| `repair_reasoning` | GLM5.3 с явно выбранным effort; отдельные сложные cases сравнивают Pro/другие варианты | Не повышать effort всем запросам. Не объявлять победителя Smart по простым календарным примерам |
| `verify_semantic` | Узкие Laya question packs с abstain; спорные случаи — отдельный верификатор | Никакого права разрешить запись или отменить жёсткий safety-guard |
| `render_verified_facts` | Детерминированный шаблон для фактов, LLM только для безопасного связующего текста | Статусы выполнения/доставки задаются ledger, не моделью |

GPT-OSS исключается из **рекомендуемого целевого набора** для обычного исполнения, repair и проверки истины. Оставляется выключенный контрольный preset для воспроизводимости, без скрытого возврата через fallback. Это не означает немедленно отключить работающую production-цепочку до готовности замены. Маленький Qwen также исключён из исполнителей записей; его возможная роль подсказчика групп требует отдельной квалификации и не наследует права записи.

Два провайдера одной модели и две модели у одного провайдера — разные резервы. GLMFlash и DeepSeek, измеренные через Together, не обеспечивают отказоустойчивости к падению Together. Маршрут проверяет `allowed role + compatible protocol + qualified preset + legal/paid endpoint + remaining budget` на **каждой** попытке, включая fallback.

Пользователь сообщил об увеличении GLM-подписки. Это учитывается как доступный ресурс, но тип продукта/endpoint/права ещё не подтверждены. Coding Plan, стандартный API и Together — разные entitlement. Не изменять платежи или автопополнение. Не имитировать coding-tool трафик из календарного daemon. Условия проверяются в #379 до выбора production-порядка.

## 4. Laya: правильная роль и измеряемая квалификация

Laya — быстрый классификатор решений, а не источник фактов. Выбор класса, вероятность выбранного класса, поле `confidence` и `act_probability` различаются. Ни одно из этих значений само по себе не является доказательством корректности.

`QuestionPack` фиксирует checkpoint/revision, версию библиотеки, язык, сериализацию state, инструкции/варианты, диапазон входа, max_len, политику truncation, таблицу калибровки и разрешённые последствия ответа. Для русского используется multilingual, а не английский root. В production процесс держит модель прогретой; cold/download/CPU/MPS и warm/concurrency измеряются отдельно.

Не объединять в один класс одновременно смысл запроса, полноту слотов, уровень риска и факт жалобы. Независимые вопросы: нужен ли read/write; каких полей не хватает; относится ли отрицание к действию; кто объект жалобы; есть ли открытый repair; какую узкую смысловую проверку запустить. Отдельная пачка questions может выполняться одним forward pass, но вопросы не должны предполагать последовательное чтение ответов друг друга.

Сначала — supervised labels на исторических задачах, отдельная calibration выборка и неприкосновенный holdout. Измерять confusion matrix, false negative опасного запроса, false accept неподтверждённого ответа, ложные блокировки, coverage/abstention и качество по языку/семейству. Проверять перестановку вариантов, цитаты, третье лицо, negation, сообщения после исправления и выход за обученное распределение. Fine-tune специфических голов/адаптеров или question packs допустим; калибровка вероятностей без исправления неверного ранжирования недостаточна.

**Локальный предварительный результат не квалифицирует Laya.** На 12 русских сценариях composite routing: English3/12, multilingual4/12; это плохая исходная постановка/нулевая доменная настройка, не рейтинг всех применений Laya. После разделения на два бинарных вопроса, 18 inputs × два порядка options: change28/36, repair23/36. Пакет двух вопросов занимал медианно20.4мс на MPS Mac. Остались уверенные ошибки; ответ выбран с вероятностью0.9979 для неверного отрицания явного создания события. Простого порога0.8 недостаточно.

Проверка «подтверждается ли фраза фактами» на 12 случаях у multilingual дала9/12 и пропустила queued→delivered. Поэтому текущую Laya нельзя ставить единственным финальным hallucination gate. Её очередь — shadow, разметка/обучение, калибровка и повторная проверка. Время20мс не является измерением Linux production.

Полный индекс разрешённых имён/коротких описаний остаётся доступен планировщику и исполнителю; никаких irreversible keyword shortlist. Узкий Laya-чек получает относящийся к вопросу evidence packet, а не автоматически полный календарь. Если требуемые для классификации данные не вмещаются, результат `insufficient_context` и дальнейшая загрузка/планировщик, а не незаметная обрезка с уверенным ответом.

## 5. Контекстный движок

`ContextPlan` — декларативный выбор разрешённых источников, полей, диапазонов и причин. Исполнитель плана сам проверяет права, scope, freshness и бюджет. Он не исполняет произвольный SQL, URL, shell, render/send или speculative writes. Между классификацией и запросом фиксируется snapshot версии пользовательского хода.

Нельзя выкинуть: actor/chat/scope и права; текущий момент и IANA-зону; активные подтверждения/выбранные объекты; последний незавершённый запрос; repair floor; ledger уже выполненных или неизвестных операций. Это небольшой структурированный блок, не пересказ модели.

Каждый добавленный блок имеет `source_ref`, `as_of`, `scope`, `resource_revision`, `selection_reason`, `cost`, `completeness`, `expires_at`, `invalidate_on`. Состояния `not_loaded`, `denied`, `empty`, `partial`, `stale`, `failed` различаются. «Ничего не загружено» никогда не превращается в «ничего нет».

Зависимости раскрываются автоматически: приглашение требует выбранного события, подтверждённого ID и прав; перенос — исходного начала/конца и свежей версии; запрос расписания — зоны, определённого интервала и доказательства покрытия. Нельзя выбирать только «похожий» текст из истории и терять связанный результат инструмента или callback выбора пользователя.

Тёплый план: постоянный короткий контракт + полный короткий индекс инструментов + заранее раскрытые нужные схемы + достаточные факты. Executor может batched-discover дополнительные схемы/чтения. Недостающий факт вызывает догрузку, а не догадку. Кеш ключуется по actor/chat/resource/range/authorization-version, имеет TTL и invalidation после изменения.

Снижение контекста допускается только если сохранены необходимые доказательства и пройден paired replay. Не прятать новые правила и полный индекс ради красивого token-count. Current synthetic estimate до истории: DM full≈14819 токенов, lazy initial≈7415, lazy read≈8288; погрешность estimator±20%. Это не реальный счёт и не доказательство ускорения. Старые lazy-прогоны добавляли раунды; смысл имеет предраскрытие, а не обязательный discovery-пинг.

Отдельный аудит фиксирует: лишние схемы/неотносящиеся prompt clauses (#511), duplicate history, излишнюю память и опасные данные; пропущенные сохранённые места (#160/PR201), pending pin (#474), picker result (#390/PR402). #519 — P0 до любого внешнего replay: credentials/auth-scene исключаются **до** записи, истории и классификации; исторические утечки требуют отдельного контролируемого remediation, не удаления данных этим PR.

## 6. Общий декларативный policy layer

Reuse boundary: общие типизированные registry фактов/операторов и safe conditions, совместимые с существующей intent/workflow схемой. У источников контекста, intent predicates, предраскрытия схем и проверок одинаковая семантика missing/unknown/scope, а не четыре похожих несовместимых языка. Не вводить второй parser рабочего диалога: #554/#559 владеют этим контрактом.

`PolicyRule`: id/version/phase, applicability, required evidence, bounded predicate, severity, allowed effect, metrics key, owner/tests. `phase`: ingress/context/pre_execute/post_execute/pre_deliver. Effects: allow,fetch_missing_context,clarify,repair_unexecuted_plan,repair_response,escalate,stop_unverifiable. Action selection отделена от проверяемого факта.

Heuristics — это прозрачные проверяемые сигналы, не секретные prompt-строки и не поиск ключевого слова для выбора модели. Пример: запрос содержит неразрешённую ссылку «это» + pending reference absent → clarify. Другой: weekday/day противоречат IANA-derived range → исправить план до записи. Никакой regex по ругательству не повышает Smart сам по себе.

Проверки имеют приоритет: auth/privacy → identity/consent/scope → factual invariants → required evidence → semantic verification → cosmetic output. Hard-deny нельзя перекрыть мягким голосованием LLM. Rule graph имеет предел глубины/итераций и детектирует циклы. Обученные правила проходят тесты и review; generated rule не включается автоматически в production.

## 7. Проверка результата, а не подсчёт tool calls

Правильная формула: **для этого утверждения/действия есть ли актуальное доказательство?**

| Ситуация | Решение |
|---|---|
| Приветствие, спасибо, объяснение возможностей | Ноль вызовов допустим; не требовать календарный read |
| Нужно уточнить неоднозначное событие | Вопрос допустим без записи; настоящий UI-формат оценивается отдельно |
| Интент уже выполнил действие и оставил trusted receipt | Новая LLM может ответить без повторного tool call |
| Достаточный свежий scoped cache с подтверждённым покрытием | Повторный read не обязателен; cite evidence manifest |
| «Завтра свободно», но диапазон не загружен/частичный | Fetch missing interval, не ответ по отсутствию данных |
| «Создано», но есть только discovery/failed call/unknown outcome | Заблокировать успех; reconcile ledger или переписать объяснение |
| Сделана запись, а prose неверно показывает время | Repair response only, без повторного создания/переноса |

Для фактов используем `Claim` с типом (event time, identity, scope, count, mutation, delivery, read coverage), значением и ссылками на trusted evidence. Дата/время/статус/ID лучше рендерятся кодом. Если LLM пишет свободный текст, извлечение claims тоже может ошибаться: шаблон или ограниченный AST предпочтительнее ещё одной слепой генерации. Неотмеченный фактический текст не должен обходить gate.

Быстрые детерминированные проверки: UTC/IANA/DST и weekday; длительность/границы; совпадение ID с подтверждённым источником; согласие на точный объект и ревизию для действий, требующих подтверждения; read range coverage; current-result versus stale-history; отсутствие лишних напоминаний; mutation applied/not_applied/unknown; delivery queued/failed/delivered. Семантические Laya-проверки применяются только к остаточным вопросам смысла, ссылок и противоречий, с известным quality profile.

Высокорисковый спор либо идёт к независимому проверяющему preset с минимальным evidence packet, либо завершается безопасным уточнением. Второй LLM не считается независимым фактом; одинаковые галлюцинации двух моделей не заменяют receipt. Для большинства очевидных ответов дополнительного LLM-вызова не нужно.

## 8. Repair и адаптивное время

Проверка возвращает не «ответ плохой», а `violation{rule,expected,observed,evidence_refs,repair_kind}`. Планировщик выбирает локальное исправление формата, догрузку факта, уточнение, повторное рассуждение на том же preset или escalation. Severity задаётся эффектом ошибки, а не раздражением модели.

На операцию один trace/deadline и один budget, включая classifier,prefetch,executor,verification и repair. Начальная политика — не более двух смысловых repair rounds; это предел, не обязательная задержка. Повторяющаяся ошибка повышает effort/другой проверенный preset, но не запускает бесконечный retry tree. Cosmetic rendering исправляется локально, без эскалации всей задачи.

Ledger неизменяемо хранит idempotency key, авторизованный intent version, resource revision и фазу каждой операции. `applied` запрещает повтор; `unknown` требует reconciliation; `not_applied` допускает исправленный план в прежних правах и свежей версии. Если пользователь меняет намерение, создаётся новая операция, а не переиспользуется ключ старой. Исправление prose не получает write-capability.

Адаптивный путь должен уменьшать, а не умножать задержку: независимые безопасные чтения/чекеры могут идти параллельно; никакой гонки двух writes. Сначала быстрые формальные проверки. В ответ передаются только подтверждённые факты; при истечении бюджета показываются выполненные действия/доказанный частичный результат и честный статус остатка. Незавершённое не выдаётся за успешное.

## 9. Исторический модельный лог: full, medium, short

Источник истины — единый версионированный набор **эпизодов**, не три разрозненных списка реплик. Эпизод содержит source references/хеши, actor/chat scope, начальную модельную БД, часовой пояс на тот момент, ordered user/system/tool/callback events, pending dialogue, допускаемые внешние результаты и независимый expected final state. Ни текущая timezone вместо старой, ни ответ бота вместо эталона не допустимы.

`full`: все пригодные восстановленные и размеченные эпизоды всех найденных источников. `medium`: стабильная стратифицированная регрессия по семействам, языкам, рискам и всем известным инцидентам. `short`: минимальный smoke, обязательно покрывающий разрешение ссылок, время, адресата, согласие, partial write, repair и приватность. Наборы ссылочные, nested и детерминированные; каждый exclusion имеет причину. Пустой или обрезанный corpus не может дать green.

Отдельная ось — длина **контекста одного и того же эпизода**: полный прошлый диалог; evidence-preserving summary; минимальный контекст с загрузкой по требованию. Expected outcome и доступная истина не меняются. Сравниваются лишние/пропущенные блоки и стоимость восстановлений. Эти три варианта нельзя путать с размером набора тестов.

Изоляция: все business handlers работают с отдельной in-memory/test БД и поддельными транспортами; auth проверяется настоящей логикой. Альтернативные инструменты проверяются через конечное состояние, а не обязательную последовательность названий. Callback/event ordering и версии сохраняются. После unknown write проигрывается реальный сценарий reconcile, не stubbing success.

Разметка отделена от настройки моделей/порогов. Split по времени/разговору/пользователю, дедуп до split; контрпримеры и парафразы не попадают в holdout из train. Для отсутствующего исходного события или старых прав результат `unreconstructable`, не созданный по догадке gold. Статистическая uncertainty и число уникальных эпизодов не скрываются повторами одного запроса.

## 10. Несмешиваемые оценки

Храним вектор, а не один pass/fail: `task_outcome`, `evidence_grounding`, `safety`, `presentation`, `availability`, `oracle_validity`, `latency`, `cost`.

- **Exact contract**: все обязательные факты, состояние и protocol constraints совпали; не byte-identical свободный текст.
- **Semantic equivalent**: та же задача и факты, корректный альтернативный инструмент/формулировка; например два timestamp с разными offset задают один instant. Никаких «плюс-минус несколько минут» для встречи.
- **Cosmetic deviation**: факт и действие верны, но тон/emoji/порядок/необязательная пунктуация отличаются. Учитывается отдельно, не блокирует успешную запись и не оправдывает ложную дату.
- **Task/semantic failure**: пропущено требуемое действие/факт, неверное локальное время в ответе, необоснованный отказ или лишнее уточнение.
- **Unsafe attempt / unsafe execution**: разные счётчики. Schema-invalid попытка не равна реально применённой ошибочной записи; блокировка guard показывает защиту, но не делает task успешным.
- **Unavailable / budget / unknown / invalid oracle**: отдельные исходы. Ни провайдер429, ни остановка бюджета не доказывает слабое рассуждение; они всё равно влияют на end-to-end completion.

Exact и tolerant результаты публикуются одновременно. Допуски фиксируются до квалификационного запуска и версионируются. Ретроспективная переоценка сохраняет raw score, причину и новый verdict, не заменяет новый валидный прогон. Отдельно first-pass accuracy,post-repair accuracy,количество repairs,false accept/reject,coverage/abstention,unsafe escapes и восстановление после сбоя.

## 11. Выполнение без потери параллельной работы

Порядок: #519 privacy barrier → #565 corpus/gold → #257 единые presets и Laya calibration → #226 context plans → #566 policy/repair integration → общий end-to-end replay → shadow/canary/exact-release verification. Реальные текущие исправления #492/#498/#515/#550/#509/#520/#522 и dialogue #554/#559 встраиваются, а не переписываются с нуля.

До rollout сравниваются абляции на одном corpus: базовый исполнитель; +deterministic checks; +Laya advisory; +context prefetch; +bounded repair. Если дополнительный классификатор ухудшает качество или p95, его ветка не включается. Стоимость повышенной GLM-подписки учитывается только после подтверждения endpoint/entitlement.

Нужны абсолютные показатели задержки и бюджета, а не обещания «мгновенно». Предварительный целевой SLO обычного успешного хода: p50<3с,p95<10с без маскировки очередей/проверок/доставки; сложный repair показывается отдельным классом. Это цель проекта, не доказанная метрика текущего production. Чистый детерминированный путь сохраняется быстрым и не делает лишний сетевой LLM-запрос ради формального статуса.
