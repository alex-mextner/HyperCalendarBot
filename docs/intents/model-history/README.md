# Модельная история для замера интентов

Это синтетическая размеченная история, на которой измеряется детерминированный движок интентов: покрытие,
точность, качество ответов и выполнение в разных часовых поясах. Готового корпуса с разметкой «какое правило и
какие вызовы инструментов верны» в репозитории не было: тикет [#565](https://github.com/alex-mextner/HyperCalendarBot/issues/565)
остаётся открытым, 667 парсер-кейсов спецификации диалога размечены без маршрута, а приватный корпус реальных
сообщений нельзя хранить в git. Поэтому история построена заново и целиком придумана.

## Что внутри

| Файл | Назначение |
|---|---|
| `conversations.dev.jsonl` | Диалоги для разработки правил. Их можно читать, разбирать ошибки и писать по ним правила. |
| `conversations.heldout.jsonl` | Отложенная выборка (не менее 30%). Не используется при написании правил: правила смотрят только на сводные числа, тексты не читаются. |
| `families.json` | Семейства поведения, типы слотов, определение «в зоне правил» и причины, по которым верный обработчик — AI. |
| `world.json` | Календарь, с которого начинается каждый диалог: 12 событий, контакты, часовые пояса. |
| `sources/*.jsonl` | Исходные файлы авторов; `scripts/intent-benchmark/build-history.ts` собирает из них выходные файлы и `manifest.json`. |
| `manifest.json` | Версия, контрольные суммы, число диалогов, доля отложенной выборки. |

Диалог — это стартовое состояние (язык, личный или групповой чат, часовой пояс, день недели и время «сейчас»,
календарь), сообщение пользователя, ответы на вопрос подтверждения и **ожидаемое поведение**: либо семейство со
значениями слотов, либо «верно отдать AI» с причиной.

## Как обеспечена независимость

- Сообщения писали отдельные исполнители, которым запрещено читать правила, шаблоны, каталог и тесты движка. Они
  видели только `families.json`, `world.json` и схему разметки.
- Отложенную выборку писали другие исполнители, чем dev, и она не видна авторам правил.
- Ожидание задаётся смыслом сообщения (слоты, написанные человеком), а не результатом разбора движком. Проверка
  (`scripts/intent-benchmark/oracle.ts`) знает только контракт инструментов и итоговое состояние календаря и не
  зависит от имён правил.
- Сообщение не может встречаться дважды; при совпадении с dev копия из отложенной выборки удаляется.
- В истории нет реальных текстов, имён, телефонов и ников: допустимы только `@ivan_petrov`, `@anna_smith`,
  `@mark_t1`. Это проверяет `test/services/intent/model-history.test.ts`.

## Определение показателей

- **В зоне правил** — одно полное однозначное сообщение с всеми слотами одного семейства. Всё остальное
  (час без «утра/вечера», нет времени или дня, массовые действия, отрицание, повторяющиеся события, несколько
  просьб, советы, болтовня) верно отдавать AI.
- **Покрытие** = верно обработанные правилом / сообщения в зоне правил. «Верно» — правило ответило, а в календаре
  оказалось именно то, что просили: название, день, время в зоне пользователя, нужное событие, приглашённый.
  Дополнительно считается покрытие всех календарных сообщений (в знаменатель входят и честно отданные AI).
- **Точность** = верные / (верные + ошибочные + ответы правила на сообщения, которые должен был получить AI).
- **Рубрика** — доля верных ответов без жёстких нарушений `docs/intents/response-quality.md` (сырые даты и JSON,
  язык не как у пользователя, нет «готово» после записи, пустой ответ без дня и календаря и др.).
- **Выполнение** — доля верных среди обработанных правилом в матрице часовых поясов и переходов на летнее время
  (шесть зон, ночь после полуночи, вечер, сутки до и после каждого перевода часов).
- **AI-ход не нужен** — доля верных ответов, после которых не запускается дополнительный ход AI.
- Метка, которой противоречат часы (прошедшее время, несуществующее из-за перевода часов, тот же день недели),
  автоматически становится «верно отдать AI»; число таких меток печатается как `relabelled`.
- Запись до подтверждения, после отказа и ошибочная запись — отдельные жёсткие счётчики; их порог — ноль.

## Как запускать

```bash
bun --no-env-file scripts/benchmark-intents.ts                       # текущий сид, обе выборки
bun --no-env-file scripts/benchmark-intents.ts --matrix 4 --write    # + матрица зон, дописать результат в docs/intents/benchmarks/
bun --no-env-file scripts/benchmark-intents.ts --history real --matrix 1 --write                # настоящая история (см. ниже), с матрицей зон
bun --no-env-file scripts/benchmark-intents.ts --gate                                           # замер обеих историй + запись docs/intents/kpi-gate.json, если правило гейта выполнено
bun --no-env-file scripts/intent-benchmark/explain.ts --outcome missed --family event.create   # разбор ошибок dev
bun --no-env-file scripts/intent-benchmark/probe.ts --clock "tue 11:16" "кто приглашён на ужин"   # как текущие правила разбирают набранные вручную фразы (для разработки правил; корпус не читает)
bun --no-env-file scripts/intent-benchmark/validate-history.ts <file.jsonl>                    # проверка исходного файла автора
bun --no-env-file scripts/intent-benchmark/build-history.ts                                    # пересобрать из sources/
```

Результаты `docs/intents/benchmarks/*.json` только дописываются: каждый файл хранит SHA исходников, цифры,
контрольную сумму и дайджест движка. Базовые замеры правил прода (ревизия 3) и ревизии 5 на движке `main`
лежат рядом; правила ревизии 3 — в `benchmarks/rules/revision-3.json`.

## Ограничения

- История синтетическая: она показывает, обрабатывает ли движок разумные формулировки, а не какая доля реальных
  сообщений попадёт в правила. Доля реального трафика измеряется отдельно (`/intent_stats`, таблица `intent_events`).
- Выборка из нескольких сотен диалогов не доказывает точность 99% на неизвестных фразах: порог точности
  проверяется, но главным барьером остаётся счётчик опасных ошибок (запись не туда, без подтверждения).
- Расширять историю можно только новыми файлами в `sources/` с префиксом `dev-` или `heldout-`; сообщения
  отложенной выборки нельзя переносить в dev после того, как по ним написаны правила.

## Настоящая история (главный замер)

Запрос владельца: покрытие 80 % должно доказываться тестами на **настоящей** истории, а синтетическая остаётся
вторым аудитом. Настоящая история лежит рядом, в [`../real-history/`](../real-history/): 552 обезличенных
сообщения 30 пользователей (в основном русский, личные чаты), собранные на сервере из `chat_history` и журнала
действий скрабберами `scripts/real-history/` (имена, места, контакты, идентификаторы заменены стабильными
псевдонимами; соответствие хранится только на сервере, режим 0600). Сырые тексты репозиторий не покидали: гейты
утечек (`test/services/intent/real-history-leaks.test.ts`) проверяют сам закоммиченный корпус.

- Метки ставили два независимых аннотатора на каждый фрагмент, расхождения решал названный в
  [`LABELING.md`](../real-history/LABELING.md) приём; согласие (каппа по маршруту 0,83–0,86) записано в
  `real-history/labels-agreement.json`. Метка «неясно» исключается из утверждений о точности, но остаётся в анализе
  покрытия.
- Разбиение (dev 356 / отложенная 183, 34 %) заморожено в `split.json`, стратифицировано по пользователю и семейству.
- Сообщения ходят через тот же слой, что и в проде; метка не вычисляется парсером и не зависит от имён правил.
- Главные показатели: покрытие среди допустимых для правил подтверждённых сообщений (отложенная настоящая, и
  объединение dev и отложенной), точность по подтверждённым меткам, «строгая» точность, рубрика, исполнение в
  матрице зон (настоящие сообщения без календарных дат), второй аудит на синтетической отложенной выборке.
- Правило гейта опирается на точечные оценки; 95 % интервалы Уилсона печатаются всегда и записываются как справочные
  поля (`docs/intents/engine.md`, «Файл гейта»).

Честные ограничения настоящей истории:

- Отложенная выборка уже **не нетронута**: при починке движка использовались два отчёта по классам (без текстов,
  по ним исправлялись общие причины), а после раунда меток в `labels-agreement.json` (`postAdjudication`) записаны
  девять правок: семь меняют маршрут или статус (шесть на dev, одна, rh-0109, на отложенной по тому же правилу), две
  добавляют допустимый вариант названия.
- Выборки малы: 38 допустимых для правил отложенных сообщений, 112 вместе; два пользователя пишут 83 % строк, поэтому
  печатается и разбивка по пользователям.
- Ровно поэтому нижняя граница 95 % интервала покрытия (75,9 % на отложенной, 78,0 % объединённой) ниже 80 %, хотя
  точечная оценка выше планки.
