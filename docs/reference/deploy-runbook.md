# Deploy Runbook

Detailed deployment reference for HyperCalendarBot. Summary in CLAUDE.md, full details here.

## .env on Server

Single `.env` file: `/opt/hypercal/.env` on the production host `root@odroidn2`. Read by `docker compose`. The DO droplet's own `/opt/hypercal/.env` serves only the external watchdog (`scripts/healthcheck-alert.sh`, see "Alert watcher").

It holds every production secret and the host is shared with other services, so `.env` and every backup of it must be mode `0600`, owner `root:root`. Plain `cp` creates a `0644` copy under the default umask; back it up with:
```bash
install -m 600 -o root -g root /opt/hypercal/.env "/opt/hypercal/.env.backup-$(date +%Y-%m-%d_%H-%M-%S)"
```
Appending with `echo ... >> .env` keeps the existing mode.

`REDIS_PASSWORD` never appears in a process argv: `docker-compose.yml` gives it to the redis container as `REDISCLI_AUTH` (read by the healthcheck's `redis-cli`) and feeds `requirepass` to `redis-server` on stdin. It must not contain `"`, `\`, `/`, `?`, `#`, `%`, a tab, a carriage return or a line feed, and redis refuses to start with an error naming the rule: the first two would be read as redis.conf syntax, and `REDIS_URL` embeds the password without percent-encoding, where `/`, `?`, `#` and `%` make the URL invalid or change the password the bot sends, and URL parsing silently drops tab, CR and LF. Spaces, `@`, `:` and the other printable ASCII characters reach both of the bot's Redis clients unchanged. The bot container receives it only inside `REDIS_URL`; the bare `REDIS_PASSWORD` from `env_file` is blanked. A normal deploy recreates only the bot, so after changing the redis service or its password recreate redis too: `docker compose up -d --force-recreate redis bot`.

Adding a new variable: write it to `/opt/hypercal/.env` on `root@odroidn2` by hand (keep mode `0600`). Hosted deploys never write `.env`; the runner user cannot read it.

After changing `.env`, **recreate** the container (not just restart):
```bash
cd /opt/hypercal
docker stop hypercal-bot && docker rm hypercal-bot
docker compose up -d --no-deps bot
```
`docker restart` does NOT re-read `env_file`.

## Diagnostics

```bash
# Docker logs (pino JSON):
ssh root@odroidn2 'docker compose -f /opt/hypercal/docker-compose.yml logs -f --tail 100 bot'

# Liveness — process started and Redis answers:
curl https://hypercal.mextner.com/health

# Readiness — everything above, plus the AI provider chain is answering.
# The alert watcher on the owner's PC polls this every 30 s; a 503 here with a 200 on /health means
# the bot is running but cannot answer anyone.
curl https://hypercal.mextner.com/ready
```

`/ready` has three answers, and the body distinguishes the last two:

| Response | Meaning |
| --- | --- |
| `503` | The bot cannot serve anyone: it has not started, Redis is unreachable, or every AI provider is failing (body says which). |
| `200 ok` | A provider has answered in this process. The bot demonstrably works. |
| `200 ok (unverified)` | The process is alive but has served nobody since it started, so it has no evidence either way. The watchdog treats this as "keep waiting", never as a recovery — a restart during an outage would otherwise look like the outage ending. After thirty minutes of waiting it drops the down-state silently, without announcing a recovery, so a quiet bot cannot end up swallowing the alert for the next outage. Any other 200 body — a proxy's own page, a changed contract — is treated the same way and logged. |

`logs/chats/{chatId}/{timestamp}.log` inside container contains detailed AI interaction logs:
system prompt, history, tool calls, responses. Enabled via `AI_DEBUG_LOGS=true`.

```bash
# Latest log for a chat (logs inside container at /app/logs/). Copy it to a private temp file and
# read ranges; never cat a whole chat log into a session (calendar data, Telegram ids):
ssh root@odroidn2 'docker exec hypercal-bot ls -lt /app/logs/chats/<chatId>/ | head -3'
# Absolute template: a bare `mktemp` honours TMPDIR, which can point inside the checkout.
umask 077; f=$(mktemp /tmp/hcb-chat.XXXXXX)   # mode 0600, outside the repository
ssh root@odroidn2 'docker exec hypercal-bot cat /app/logs/chats/<chatId>/<timestamp>.log' > "$f"
grep -n '^## ROUND\|^## FINAL\|^## END' "$f"; sed -n '<from>,<to>p' "$f"
rm -f "$f"

# Docker logs around an incident: warnings and errors plus the records that exist for a delivery.
# A FINAL answer is recorded before delivery and does not prove it, and a successful ask_user send
# logs nothing: a missing delivery record is unknown, not failure.
#   AI request metric (level 30; deliveryOutcome delivered|fallback|discarded)
#   Finalize edit failed / Finalize send failed / Writer finalize failed (level 50)
#   Delivered via bot API / Delivered via the inviter's own Telegram account (level 30, invitation sent)
#   Bot API + inviter session failed — deep-link fallback attempted (level 30, invitation not delivered)
#   Delivery chain failed (level 50)
ssh root@odroidn2 'docker logs --since 3h hypercal-bot 2>&1 | grep -E "\"level\":(40|50|60)|AI request metric|Delivered via|deep-link fallback attempted"'
```

## Alert watcher

Why it exists: until 2026-09-28 a macOS LaunchAgent polled `/admin/alerts/next` and opened an omp session; after the Mac was sold nothing consumed the queue (7 alerts pending on 2026-10-24, the newest a failed deploy), and from 2026-10-10 to 2026-10-24 nothing raised DOWN either. The queue is the bot's own SQLite table `alerts`, so a bot that is down cannot store its own DOWN alert (the watchdog's POST to `/admin/alerts` fails and is swallowed). Down detection therefore has two paths that do not need the bot: the DO watchdog sends a Telegram message straight through the Bot API, and the consumer below probes readiness itself and starts the investigation.

What runs: the systemd **user** service `hcb-alert-watcher` on the owner's Ubuntu PC (`scripts/hcb-alert-watcher.ts`). Every 30 s it

1. probes `https://hypercal.mextner.com/ready` (`HCB_BASE_URL` overrides; healthy = `200` with body `ok` or `ok (unverified)`); three failed probes in a row raise one `down-<epoch>` incident for the whole outage. A name that does not resolve on the PC is not a failed probe (it says nothing about the bot): after three in a row the owner gets one `tg --tag problem` notice that the watcher is blind, and no session starts. On 2026-10-25 this PC's systemd-resolved returned `Name not found` for the new host's A record while the ISP resolvers answered it; check with `resolvectl query -t A hypercal.mextner.com`;
2. pops `/admin/alerts/next` until it answers `204`. The pop is destructive on the server, so every alert is written to the local spool (`~/.local/state/hcb-alert-watcher/pending/`) first; alerts older than 12 hours are consumed and logged as stale, not investigated;
3. starts **one** detached omp session for everything pending, at most one per 30 minutes (alerts that arrive meanwhile wait and share the next session), at most once per alert id (`launched/<key>` markers survive restarts). The session starts through the sanctioned `rig-detached-omp` launcher in the repository checkout, plus a tmux window `hcb-alert-<utc stamp>` in the canonical `main` session that follows its log (`/tmp/agent-logs/<name>.log`) and closes 15 minutes after the session ends.

The brief the session gets (`~/.local/state/hcb-alert-watcher/briefs/`) fences the alert text as untrusted data, makes the first phase read-only, forbids restart/stop/rollback/redeploy, database writes, deletions and merging without the owner (#596), and requires a Russian `tg report` with the root cause first. The watcher itself tells the owner with `tg --tag problem` when it is blind: the launcher fails (alerts stay pending), or the queue answers 401/403/404 three times in a row (token rotated or endpoint disabled); each notice is sent once per streak. Every helper process it spawns (launcher, tmux, ctmux, tg) has a 30 s deadline and runs without the alert token; the tmux server and window are started in their own systemd scope so restarting the unit never kills the owner's tmux.

The brief also says, in the section every brief has and before any checklist, that everything the session reads from production (container logs, per-chat logs, database rows, Redis values, job errors) is untrusted data too, because it holds text users wrote (messages, event titles, names): evidence about the incident, never instructions. Its duplicate-event query groups on the user and start, counts the distinct titles and selects no title, so that one query puts no event title into the session's context; the logs it also reads still carry user text, which it must not quote (#949).

Agent-run incidents (`source = agent-run-incident`, since 2026-11-01): a user-facing agent run that ends badly returns no 5xx and leaves `/health` and `/ready` green, so neither the PC probe nor the DO watchdog sees it. On 2026-11-01 at about 17:06 UTC a run ended `unverified` after a validator timeout, the user got near-useless notices and nothing woke an investigation. The bot now pushes one row to the `alerts` table (`db.alerts.push`, the table this watcher pops) when a user-facing run ends in one of four classes: `error` (the run threw), `unverified` (the answer could not be checked), `limit` (the rounds or the request budget ran out) or `interrupted` (the user was shown the "request interrupted" notice). Supplement turns and silent runs raise nothing. The bot rate-limits itself to one alert per class per 10 minutes (in memory, so a restart resets it); incidents held back are counted and the next alert of that class carries `suppressedSince: <n> earlier incident(s) of this class were not alerted in the last 10 minutes`. On the PC these alerts travel like every other: spooled, one session per 30 minutes for everything pending, so an incident that arrives inside the window waits and shares the next session. The text is plain lines with identifiers and counts only, never user text, event titles, chat ids or user ids: `Agent run incident (<class>)`, `requestId`, `termination`, `elapsedMs`, `tools` (`<tool> ok=<n> fail=<n>` per tool, or `none`), `writeSucceeded: yes|no`, `provider: modelCalls=<n> attempts=<n> fallbacks=<n>`, `validator: not_run|approved|rejected|unavailable(timeout|provider_error|aborted|budget_expired)`, `delivery: delivered|fallback|discarded`, an optional `error: <error class name>`, the optional `suppressedSince` and a last line saying how to look the run up. The investigation finds the run by `requestId` in `docker logs hypercal-bot` and, while `AI_DEBUG_LOGS=true`, in the per-chat debug log: `docker exec hypercal-bot grep -rl 'REQUEST ID: <requestId>' /app/logs/chats` names the file (one `REQUEST ID:` line per run). A run with debug logging off, or older than that line, is found through the `chatId` on its start line in the container log and read from `/app/logs/chats/<chatId>/` by time. For this source the brief adds a checklist (the alert's `source` switches it on, never its text; the class on the first line only picks an extra block): every requestId (one chat can have two overlapping runs), the write receipts against the `events` rows including duplicates (one user and start written twice, with the same title or a retry's differently worded one; the query counts every copy, deleted ones too, across all rows and selects no title; `created_at` is compared in its stored form `2026-01-02 03:04:05`), what the user actually saw, host load (`/proc/pressure`, swap) and the `image-render` queue, and the validator and provider timings in the `AI model call metric` lines. It reports only: it never replays a write, resends a message, or edits or deletes a row (unknown completion is not failure, AGENTS.md), and it reuses an existing ticket (`task find`) before opening one.

Install (idempotent; the token lives only in the keychain as `hcb-alert-watcher/admin-alert-token` and reaches the service through `keychain exec --caller hcb-alert-watcher`):

```bash
scripts/install-alert-watcher.sh --fetch-token-from root@odroidn2   # first time: also copies the production ADMIN_ALERT_TOKEN into the keychain
scripts/install-alert-watcher.sh                                    # later: update unit, restart only if it changed
HCB_BASE_URL=https://other.example scripts/install-alert-watcher.sh # probe another public host (written into the unit; re-run without it to drop it)
scripts/install-alert-watcher.sh --uninstall
systemctl --user status hcb-alert-watcher; journalctl --user -u hcb-alert-watcher -f
```

Run it from a checkout whose `main` contains the watcher; the unit points at the canonical checkout, not at a worktree. Install it on the machine that hosts the owner's omp sessions only (the home laptop does not need it: a second watcher would pop alerts the first one then never sees). Tuning is by `HCB_*` environment variables read by `loadConfig` in the script (`HCB_ALERT_POLL_SECONDS`, `HCB_ALERT_RATE_LIMIT_SECONDS`, `HCB_ALERT_DOWN_PROBES`, `HCB_ALERT_STALE_HOURS`, `HCB_ALERT_COMMAND_TIMEOUT_SECONDS`, `HCB_BASE_URL`, `HCB_ALERT_STATE_DIR`).

Dependencies (2026-11-04): the script imports `zod`, so the canonical checkout needs its `node_modules`. On 2026-11-04 the checkout had none (a fresh clone is never installed by itself): after a restart the unit looked installed but exited at once with `error: Cannot find package 'zod' from '.../scripts/hcb-alert-watcher.ts'`, restarted every 30 s, and nothing consumed the queue until someone ran `bun install --frozen-lockfile` there (#949). Use the system Bun and never a symlinked `node_modules` (AGENTS.md). Three rules:

1. Before the first install, and before a backlog triage run (below) on a fresh clone: `(cd <canonical checkout> && bun install --frozen-lockfile)`.
2. Before EVERY restart that follows a re-clone, a `git clean` of the canonical checkout or a merge that adds an import (the 2026-11-04 loop happened without any `package.json` change, `zod` was already declared), run `scripts/install-alert-watcher.sh --dry-run`: it runs `bun build scripts/hcb-alert-watcher.ts --target bun` (the real import graph, nothing executed), changes nothing and refuses before any unit is written or started. A plain `scripts/install-alert-watcher.sh` does the same check and then installs, and starts the service when it is stopped, so do not use it while the service is stopped on purpose (backlog triage below). A refusal prints the head of Bun's own error; it adds the exact install command only when the error says a package is missing (`Could not resolve: "<package>". Maybe you need to "bun install"?`) or that a file under `node_modules/` lacks an export (a stale install); a syntax error or a missing local file gets no install hint, because `bun install` does not fix it.
3. After ANY merge that touches `package.json` or `bun.lock`, always run `(cd <canonical checkout> && bun install --frozen-lockfile)` first, even when the check passes: `bun build` proves only that every import resolves, not that `node_modules` matches `bun.lock`, so a stale package that lacks a method the new code calls passes the check and then throws at load, restarting the unit every 30 s.

Then `systemctl --user restart hcb-alert-watcher`. The check runs only when the installer runs, so a restart without it can still loop silently (#842).

Backlog triage (alerts that piled up while nothing consumed the queue): the service pops the whole queue on its first cycle and, with the default 12 h limit, marks old alerts stale without investigating them, so triage BEFORE the first install (or after `systemctl --user stop hcb-alert-watcher`): `keychain exec --caller hcb-alert-watcher --env ADMIN_ALERT_TOKEN=hcb-alert-watcher/admin-alert-token -- env HCB_ALERT_STALE_HOURS=1000 bun scripts/hcb-alert-watcher.ts --once` (the pending alerts go to one session; one run pops at most 50, so with a bigger queue repeat it, after the 30-minute rate limit, until the log shows no `queued from` line), then install or `systemctl --user start hcb-alert-watcher`. Never run `--once` while the service runs: the two processes share the state directory without a lock and could each start a session. A 200 from the queue that the watcher cannot parse is kept in `~/.local/state/hcb-alert-watcher/unreadable/` (the server's pop already consumed it; one file per cycle at most). A launcher that hits its 30 s deadline is not retried (the session may already run): the owner is told once and the alerts are marked handled. After a restart in the middle of a launch, a claim whose session log (`HCB_AGENT_LOG_DIR`, default `/tmp/agent-logs`) already exists is confirmed, not launched again.

Known limits: the probe runs on the PC, so a PC that is off or offline raises nothing (the DO watchdog still messages the owner then), and a PC whose own network is down counts as a down bot after three failed probes (cached DNS still answers); failures more than about six minutes apart (suspend, service stopped) never add up to an outage. The DO watchdog posts its queue alert only while the bot is up, so only the PC probe turns a hard outage into an investigation session. The unit and every session it starts run with `PATH=~/.local/bin:~/.bun/bin:/usr/local/bin:/usr/bin:/bin` and no ssh agent (key-file auth to `root@odroidn2` works, verified under `systemd-run --user --pipe`); the installer warns about `omp`, `gh`, `ssh`, `tmux`, `ctmux`, `systemd-run` missing from that PATH and pins `tg` by absolute path. After a failed launch the launcher is left alone for a minute.

Also known: (1) an outage seen by the PC probe and, separately, by a queued alert (the DO watchdog's POST, a crash alert) can start two sessions 30 minutes apart: dedupe is per alert id and per probe incident, not across sources; the second session's brief tells it to check `omp-steer list` first. (2) The unit starts at login or boot (linger); if the keyring is still locked, `keychain exec` fails with its own exit code, which `RestartPreventExitStatus=78` does not cover: the unit restarts every 30 s without being able to tell you. After a reboot check `systemctl --user is-active hcb-alert-watcher`; `keychain unlock` fixes it. (3) Bun loads the script once: after a merge that changes `scripts/hcb-alert-watcher.ts` or `package.json`/`bun.lock`, first follow the three dependency rules above (`bun install --frozen-lockfile` in the canonical checkout, then `scripts/install-alert-watcher.sh --dry-run`), then run `systemctl --user restart hcb-alert-watcher` (the installer restarts only when the unit text changes). (4) A pop whose response times out before any header arrives may have consumed an alert on the server; only the journal line "queue step failed" shows it. (5) The queue poll refuses redirects so the token never travels to another host.

Probe failures under host load (2026-11-01): `state.json` showed one failed probe at 17:30:38 UTC (`lastProbeFailureAt`, the consecutive count back to 0 afterwards) and the journal had no line for it, because a single failed probe was not logged. It was a timeout, not an outage: cloudflared on the odroid logged `Incoming request ended abruptly: context canceled` for `hypercal.mextner.com/ready` at 17:30:38, the instant the watcher's 20 s `HCB_ALERT_PROBE_TIMEOUT_SECONDS` deadline fired (a second `/ready` request from an unidentified client ended the same way at 17:30:34). The bot's own log for that window holds only a Google pull-sync job that needed 46 s to apply zero items (it also waits on Google, so that alone proves little). About 18:00 UTC the host still showed load average 11-12 on 6 cores, 3 GB of 6 GB swap in use on the microSD, `/proc/pressure/io` `full avg300` above 50%, and `/ready` answered from this PC in 13.6 s, 1.9 s and (once) not within 25 s: a swapping odroid answers late, not wrongly (memory pressure on the odroid: #800). Each failed probe before the incident threshold is now logged with its reason, `readiness probe failed (1/3): no answer within 20s (probe timeout)` against `no response (<error>)` or `HTTP <status>`, so a blip shows in `journalctl --user -u hcb-alert-watcher`. Three timeouts in a row still raise a `down-<epoch>` incident, on purpose: a bot that needs more than 20 s to say it is ready is not serving users either, and the investigation reads the host load. Raise `HCB_ALERT_PROBE_TIMEOUT_SECONDS` only to judge a degraded host differently, not to hide it. Timestamps: the PC journal and the odroid journal print local time (CET, UTC+1 since 2026-10-25), so give `journalctl --since '2026-11-01 17:25:00 UTC'` and `docker logs --since 2026-11-01T17:25:00Z` an explicit zone. The same limit makes known limit (4) likelier: a queue pop that times out at the same 20 s may have consumed an alert on the server (the pop is not acknowledged), so an incident raised while the host is starved can be the one that is lost; only the journal line `queue step failed` shows it.

### Validator outage after writes

The final answer of an agent run is checked by a response validator (a model call). When it cannot reach a verdict (`validator: unavailable(<cause>)`: timeout, provider error, aborted or budget expired) and the run already executed calendar writes, the bot sends a deterministic receipt-only confirmation built from the write receipts (exact titles, dates and times). It never runs the retry-with-tools pass, because that pass could replay writes the user already has, and it never says "request interrupted" when every tool succeeded. A validator outage is not evidence that the answer is wrong: the run ends `unverified`, one `agent-run-incident` alert is queued, and the investigation reads what the user actually received. The validator runs on its own 16 s clock; once the request budget is spent it launches nothing and only the local checks decide.

### Timeout alerts

Every timeout the bot hits goes through `reportTimeout()` (`src/services/incident/timeout-reporter.ts`) and reaches the alerts queue as source `timeout`: at most one alert per kind (`validator`, `provider`, `agent_request`, `http`, `render`, `model_listing`, `claude_credential`, `chat_run_lease` (a message stopped waiting for a hung run ahead of it in its chat, counted once per hung run), `chat_run_reservation` (a message's handler outlived its reserved place in the chat's line), `agent_drain`, `google_refresh_lock`, `db_busy`, ...) per 10 minutes, with the `unrecovered` and `recovered` counts since the last alert. A timeout a provider fallback absorbed is `recovered`: counted, never dropped, so a trend is visible. The alert holds kinds, durations and counts only, no message text, user ids or titles. The investigation treats `unrecovered` ones as incidents and a burst of `recovered` ones as a capacity signal (host load, swap). A locked SQLite database has no timer to hook: the central error handlers and the places that swallow a database error hand what they caught to `reportIfDatabaseBusy()` (`src/services/incident/database-busy.ts`), which reports a `SQLITE_BUSY` as `db_busy`. `test/services/incident/timeout-sites.test.ts` checks every callable in `src` (not every file) that arms a deadline (`AbortSignal.timeout`, `setTimeout`, `Bun.sleep` poll loops, `Promise.race`, BullMQ `waitUntilFinished`, a client `timeout` option, a `TimeoutError`, `busy_timeout`): it must call `reportTimeout()` / `reportIfDatabaseBusy()` itself or sit on that file's exemption list with a reason, and an exemption that is reported elsewhere must name a callable that really reports. A callable that arms two deadlines and reports once is the one case the check cannot tell apart.

## Agent runs per chat and repeated creates (#929, #520)

GramIO hands every Telegram update to its handler without waiting for the previous one (`EventQueue.process` in `@gramio/composer` 0.3.4, webhook and long polling alike), so two messages of one chat used to run two agents at once; on 2026-11-01 two quick «Да» created every event twice. Now `CalendarBotAgent.run` goes through `ChatRunGate` (`src/services/ai/chat-run-gate.ts`): one run at a time per chat id, first come first served, other chats unaffected. This covers every caller (message pipeline, `/cal`, button continuations, voice, scheduled AI).

- The place in a chat's line is reserved when the message is saved, in the same synchronous step (`chat-logging` middleware → `CalendarBotAgent.reserveChatTurn` → `ChatRunGate.reserve`), not when its handler reaches the agent: a handler that waits on a scene or retry lookup first cannot be overtaken by a message saved after it. The update's handling runs inside that reservation (`withChatTurn`, an async context, `src/services/ai/chat-turn-context.ts`), so the agent run it starts (text pipeline, `/cal`, a button) takes the place over with no id passed along; a run started elsewhere (scheduled, retry) finds none and joins the end without a message of its own, whatever row id it borrows for the action log; the reservation is released when the update's handling ends (an intent answered it, a command, an error) or after 60 s unused (`Not waiting any longer` / `A reserved place in the chat was never used` in the log).
- A queued run starts after the earlier one has written its turn. It re-reads the user and the ±2 week schedule and reads its own message after the earlier run's rows (`ChatHistoryRepository.placeUserTurnAfterLatest` sets `chat_history.turn_order`; the row keeps its id, so the action log, the per-user `chatHistoryIds` map and built contexts stay valid). Only a run that took over a reserved place has an own message to place (and only after a bot row of the same conversation, private or group); scheduled/synthetic runs borrow the user's latest row id for the action log and never move it. It is not shown turns queued behind it, in its history or through `get_history` (`ctx.deferredTurnRowIds`), so its model reads «request, what was done, this message». The request budget (90 s) counts from the start of the run, not from arrival.
- A turn that waited is moved by reading position only, never in time: its `chat_history.created_at` stays the time the user sent it, `turn_order` records the move, and the history readers order a row by when it reads (the time of the newest row it was placed behind), then `turn_order`, then id. The model is shown such a turn with `[queued: …]` after its timestamp (`QUEUED_TURN_MARKER`, explained in the system prompt) and the day-reference guard ignores every row saved after the message when it looks for the `ask_user` question the message answers, so a message sent while an earlier run was still working is never read as the answer to a question that run asked afterwards (a queued «Да» could otherwise confirm a duplicate, a forced create or a delete nobody offered it). A button answer, which explicitly belongs to the question it was tapped under, still binds to that question. A voice message takes its place in the line when its transcript row is saved (`handleVoiceMessage`), like a text message.
- Known limits of the queued-turn rule (#929, #953, #957): (1) a button tap that waited behind a run started by another user message, or a reply that reached the chat before the asking run wrote its turn, is also read as queued and the guard loses the question's day; the model is then told to ask what it refers to, it is never executed on a guess. The guard infers the question from row order, it is not carried on the button. (2) The refusal to treat a queued «Да» as consent for `allow_duplicate`, `force` or a delete confirmation is the system prompt plus the guard: no tool handler checks it (a delete still needs the bot's own button tap). (3) A voice transcript can be bound to a question saved while it was being transcribed (#953).
- A run that never finishes holds the chat for at most its budget plus 30 s (`CHAT_RUN_GRACE_MS`); then the next run goes on and the log says `Not waiting any longer for the earlier agent run in this chat`. A queued run is in `CalendarBotAgent.inFlight`, so the shutdown drain waits for it; at shutdown the wait ends at once and the run takes its normal fail-fast path (notice and stored retry), so no queued message is dropped.
- Log lines to look for: `Agent run started after waiting for the previous run in this chat` (`waitedMs`, `queuedBehind`) and `Routing to AI agent` with `updateId`/`messageId`: the same ids twice mean a Telegram redelivery, new ids a second message.
- While a message waits the chat shows the typing indicator (refreshed every 4 s). If the run ahead outlives its lease (`CHAT_RUN_GRACE_MS` after the 90 s budget, so about 120 s of waiting for the run directly ahead; the lease bounds the wait for that one run only, so the Nth message in a long queue of slow runs waits for every run ahead of it in turn, up to about (N-1) leases), the waiting message goes on beside it and the user is told once per hung run (`agent_queue_lease_expired`, ru and en): the first later run that has a message of its own to show it announces that the earlier run was given up on, and a run without one (scheduled, or a supplement) never uses the notice up for the next. `Agent run started` and `Agent run complete` carry `updateId`/`messageId` too.
- Every kind of run uses the gate, keyed by its chat id: supplement runs (silent, optional text: no typing, no notice, so a supplement can sit behind a main run for up to the same ~120 s and then speaks to nobody) and scheduled/system runs (their chat is the user's private chat, so a scheduled reminder run waits behind an active conversation and vice versa). The worst case for any run is that wait plus its own 90 s budget.
- `create_event` (`EventRepository.createUnlessDuplicate`, one immediate SQLite transaction, so it holds across connections and restarts) compares with the live events of the same calendar (a one-off only with one-offs, a series only with series of the same recurrence rule; the owner's own events with no Google calendar, the `primary` alias or the id registered as the user's primary calendar, a secretary's `owner_id`, or the same group; events imported from a secondary Google calendar never count) that have the same title (trimmed, whitespace collapsed, case folded) and all-day flag. A series is matched only as an exact repeat within the window (`duplicate`), never by `same_day`:
  - `duplicate`: same start and end (all-day: the same floating dates, as `allDayDates` reads them), the same description, location and reminders the caller stated, created within 10 minutes (`RECENT_DUPLICATE_WINDOW_MS`). It comes back as `Event already exists …`: success, `alreadyExists` on the tool result, no second row, reminders, notifications or calendar push.
  - `same_day`: any other candidate on the same local day, whatever its age (the «move by creating» case of #520): `SAME_DAY_EVENT` error, `mutationState: not_applied`, pointing at `update_event` with the existing id.
  - The model makes a deliberate second copy with `allow_duplicate: true`.
  - The event row and its reminders are written in the same transaction (also for `allow_duplicate` and every other `EventService.createEvent` caller); a failed reminder write leaves no event, so a retry starts clean. All-day dates are read in the zone each event was saved with.
  - The result of a repeat is `success: true`, `mutationState: not_applied`, `alreadyExists`. Intent answers: it is carried through `intent-executor` into `ToolAnswer`, and both the renderer and a closing `respond:` step (`basis.event.create`, `basis.event.create_invite`) say the event is already in the calendar instead of «created». The run-failure receipt wording («Completed: Create event») lives in `write-outcomes.ts` and is left to the receipt rewrite tracked in #929.

## Asynchronous pictures (AI picture tools, 2026-11-01)

Why: on 2026-11-01 (prod `bb7a9d47`) `render_day_image` / `render_week_image` / `render_month_image` / `render_table` waited for the BullMQ render inside the agent turn. On the loaded odroid real renders took 73–80 s (`Job wait render timed out ... 45000ms`, `Day image render failed`); two waits plus model rounds spent the ~90 s turn budget, the answer validator timed out and the user got the aborted-run notice instead of the text the model had already written (tracked in [#799](https://github.com/alex-mextner/HyperCalendarBot/issues/799) and [#800](https://github.com/alex-mextner/HyperCalendarBot/issues/800)).

Now the tool only enqueues (`src/services/image/image-delivery.ts`, `ImageDelivery`) and returns at once: `success`, an output that says the picture "is being prepared and will arrive in the chat as a separate message", and a hint to the model that it is queued, NOT sent, and must not be called "attached". The turn ends with the text. In the background the service renders, sends the picture to the same chat as its own message (photo, or document when oversized, then the best-effort pin) and logs exactly one line `Image delivery outcome` with `outcome` = `delivered` (with the Telegram `messageId`) / `failed` / `timed_out` / `superseded` / `interrupted`. The line carries the picture kind, job type, chat id and timings, never user text.

Owner instruction of 2026-11-01 (Telegram message 26331): ALL pictures are asynchronous, and every timeout goes to the repair flow. So the same service now carries every other picture the bot sends; nothing in the bot awaits a render any more (`RenderService.renderDirect` is called only inside `ImageDelivery`):

- `/today`, `/tomorrow`, `/week`, `/month` (`src/bot/commands/*.ts`): the text answer goes out first, then the picture is queued with `queuePicture` (`src/services/image/queue-picture.ts`) and arrives as its own message when ready (`/today` and `/month` pin it, as before). Without `imageDelivery` (no Redis, Playwright failed to start) the commands stay text-only.
- The agenda buttons (`imd:` daily, `imw:` weekly, `src/bot/handlers/callback/agenda-routes.ts`): the callback query is answered at once, the picture follows as a reply to the tapped message. A second tap on the same picture while it is pending is a duplicate and gives no second picture.
- The conflict picture the inviter gets when an invitee accepts (`invitation-notify.ts`): queued the same way, sent to the inviter's chat, with the note "schedule comparison" if it fails. Before this change a failed or timed-out render was only logged.
- The scheduled morning/evening digest has no picture path: the `image` format is still sent as text (`TODO(#863)` in `src/services/notification/scheduler.ts`), so it never waited for a render. When #863 adds a photo it MUST go through `queuePicture`.

The delivery id is deterministic: chat id, the Telegram message id of the command (or the callback query id of the tap, or `invitation:<id>:<callback query id>` for the conflict picture: answering the invitation again after a failed picture asks for a new one, a redelivered tap does not), kind, slot and payload, so a duplicate update or a double tap is one render and one picture. A failed, timed-out or oversized picture gives the user exactly one note and a timed-out one also reaches the alert queue as `reportTimeout({ kind: 'render' })`, for the commands and buttons exactly as for the AI tools. The payload hash covers what the picture shows, not the clock: the current-time line and the "Today" badge of a picture of today (`currentTimeMinutes`, `relativeDay`) are left out, so the same picture asked again in another minute is the same delivery (`duplicate`) and only a change of the data replaces the older pending picture (same slot, newer payload) instead of stacking a second one.

Limits, all constants in `image-delivery.ts`:

- Hard bound: `IMAGE_DELIVERY_BOUND_MS` = 150 s from the tool call to the end of the render (twice the worst render seen on 2026-11-01, 73–80 s). The job carries it as `expiresAt`; the worker drops a job that only starts after it (stalled job re-queued by a restart, retry) with `UnrecoverableError`, so no render happens for nobody. The upload of a finished PNG has its own `IMAGE_SEND_BOUND_MS` = 30 s.
- Per chat at most `MAX_PENDING_PER_CHAT` = 2 pending pictures, at most `MAX_PENDING_TOTAL` = 12 on the bot (a delivery that already ended and is only telling the user holds no place; that note is bounded by the send bound); a further request is not queued and the tool says so (`imageBusy`). The schedule comparison of an accepted invitation (`kind: conflict`) has its own limits and does not count against the chat's 2: `MAX_PENDING_CONFLICT_PER_CHAT` = 4 per chat and `MAX_PENDING_CONFLICT_TOTAL` = 6 on the bot. Three guests accepting within one render would otherwise lose the third comparison for good (no command can ask for it again), and two pending comparisons would refuse the inviter's own `/today` and AI pictures; the bot-wide share keeps the other half of the 12 places for the chats' own pictures. The limits are bounded, not removed: two accounts accepting each other's invitations can still hold the 6 comparison places for up to 150 s (ticket #969). The identical picture requested twice (same slot and same payload) is one render and one delivery; a newer picture of the same slot (same day / week / month / calendar, changed data) replaces the older pending one, so the user gets only the newest. The older one is recorded `superseded` at the moment of replacement, not when its run unwinds, so a shutdown in between cannot leave its row `queued` for the next start to send after the newer picture.
- Staleness: a calendar write for the picture's data while it renders (domain events `myCalendar.newEvent`/`updatedEvent`/`deletedEvent` and `myGroup.newEvent`; a group picture is stale after ANY write by any user, it is not keyed by group) makes the finished picture be rebuilt once from the current data instead of showing the old state beside a text that already states the new one. A rebuild whose render data is identical is skipped (see below), so an unrelated write costs a comparison, not a render. Writes that emit no domain event do NOT trigger it: Google pull sync, group event update and delete (`EventService.updateEventForGroup`/`deleteEventForGroup`) and the recurrence writes (cancel or edit one occurrence, split, delete the future ones); a picture in flight then shows the state before that write. Known gap, ticket #964.
- The rebuild only runs with at least `REBUILD_MIN_BUDGET_MS` = 45 s of the bound left; with less, or when the rebuild fails, the picture already rendered is sent (an older state beside newer text beats no picture and a timeout alert). A rebuild cut by the render bound is still reported as `reportTimeout({ kind: 'render', recovered: true })`, so a slow host stays visible although the user got a picture.
- A write that leaves what the picture shows unchanged (the rebuilt render data is identical) is not rendered a second time. After a rebuild the picture on its way counts as the new data, so the same request again is `duplicate`, not a newer picture that replaces it. The slot of an AI picture ends with the user's language, and a group picture's slot also carries the requester (`group:<chat>:viewer:<user>`, for the AI tools and the day/week buttons alike: its holidays are the requester's), so two members of one group chat never replace each other's picture.
- The same request again (same Telegram message, same picture) after its delivery ended is `settled`: nothing is queued, the AI tool says it was already handled (`imageAlreadyHandled`), a command is silent. While the first one is still live it is `duplicate` ("being prepared"). A new message asking for the same picture is a new delivery.

What the user gets when the picture does not arrive: exactly ONE short note in their language naming the picture (date, week, month or table title) and offering to ask again; never the internal error. The schedule comparison of an accepted invitation is the exception: no command or tool can request it again, so its notes (`imageNote*Final`) do not offer it, and a job that cannot even be built says so in its own words (`invitation_conflict_picture_failed`) instead of pointing at a text version that does not exist. A picture that is undeliverable by nature (over the 50 MB document limit, a raster over the allocation limit) gets the localized note `imageNoteUndeliverable` ("too large to send, ask for a shorter period or a smaller table"; `imageNoteUndeliverableFinal` for the schedule comparison), never the renderer's English message, and is not an incident. A supplement turn (silent optional text after an intent answer) queues no picture at all: its sender drops everything, so the picture could only block or supersede a real one.

An upload that ends in anything but Telegram's own refusal (a 4xx answer) is an uncertain send, because the picture may have landed: a dropped connection, an abort or a 5xx answer is recorded `unknown`, nothing is sent again, and the owner's repair flow gets one `render-failure` alert (`errorName: UncertainSend`). The user gets one note that does not claim a failure either way ("may not have arrived: the upload was cut off, ask again if you do not see it", `imageNoteUncertain`): the answer of an AI turn may have been only this picture (a `[SKIP]` text beside a queued picture counts as answered, #508), and without the note a user whose upload died would be left with nothing. The note is guarded by the delivery's own end alone (an `unknown` row is never in the recovery pass). Only a 4xx refusal is `failed` with one note and a `render-failure` alert. A refusal that asking again cannot fix (403 bot blocked or removed, 404 or 400 "chat not found", 400 "not enough rights to send photos") tells the user in its own words that Telegram does not let the bot send pictures in this chat (`imageNoteRefused`, no offer to ask again), logs at warn and raises no alert, the same rule as the broadcast worker's permanent failures. An upload that hangs past its bound is `unknown` too, tells the user the same uncertain note and reports `reportTimeout`.

What reaches the repair flow (alerts queue -> `hcb-alert-watcher` -> omp session, see "Alert watcher"):

- A render that does not finish within the bound: `reportTimeout({ kind: 'render', elapsedMs, limitMs, recovered: false })`, one aggregated alert per kind per window with `source` `timeout`, as for every other timeout of the bot (`src/services/incident/timeout-reporter.ts`). A hanging upload (the note says only that the picture may not have arrived: it may still land) reports the same kind with the send bound as `limitMs`.
- A render or upload that fails for another reason: one aggregated alert per 10 minutes of its own kind, `source` `render-failure` (`src/services/image/render-failure-reporter.ts`), with the picture kind, job type, error class name and durations (never the message text, user text or ids), and how many were held back since the last one. Failures inside the window are held back and sent as ONE summary when the window ends (tried again after 60 s while the alert queue refuses it, and a first failure the queue refused is held and retried the same way, so a lone failure is not lost), or at a graceful shutdown; a process killed without one loses the held summary.

Durable deliveries (migration `070_image_deliveries`, [#936](https://github.com/alex-mextner/HyperCalendarBot/issues/936)): every picture has one row in `image_deliveries` with a deterministic id (hash of chat id, the user's message id, kind, slot and payload; also the BullMQ job id, so a repeated add is a no-op and a restarted bot finds the same job). The row is written BEFORE each step: `queued` at enqueue, `rendered` when the PNG is in hand, `sending` before the Telegram call, then `delivered` (with the Telegram `message_id`), `failed`, `expired`, `unknown` or `superseded`. Terminal rows drop their payload and are pruned once 7 days old, at the next start (the start-up reconciliation is the only caller). A finished render stays in Redis for 3 minutes (`removeOnComplete`, just over the bound) so a picture finished while the bot was down can still be collected.

Restart and shutdown: shutdown closes `imageDelivery` right before the image queue (see `shutdown.ts`). Local waits are cancelled with the reason `shutdown`, which keeps the queued BullMQ job; no note is sent and each delivery is logged `interrupted` with `resumable: true`, its row stays `queued`. A picture already being uploaded gets a 1.5 s grace: if it lands it is `delivered`, otherwise it is `unknown`. A completion that arrives after the close finds nobody to send to and is dropped, never reported as delivered. Only a delivery without a store (tests, dev) tells its user at shutdown. The same close sends the `render-failure` summary still held back for its 10-minute window (`RenderFailureReporter.flush()`), so a deploy right after a burst of failures does not lose it; a SIGKILL or a crash still does.

Start-up reconciliation (`ImageDelivery.reconcile()`, called from `src/index.ts` once the bot exists, fire-and-forget; recovery sends through `recoverImageDeliveries` in `src/bootstrap/image-render.ts`):

- `sending` (the upload started, its end is unknown): marked `unknown`, never retried because a retry could send a second picture, and the user is not told (known gap, ticket #969: `reconcile` holds `transport.notify`, but `markNoteSent` claims only `failed`/`expired` rows, so a note for an `unknown` row needs its own once-only claim; the same gap exists for an upload the shutdown grace gave up on). One aggregated `render-failure` alert (`errorName: UncertainSend`) so the owner's repair flow hears of it. Whether the picture reached the chat is only visible in the chat; the `messageId` is not known.
- A `sending` row whose last update is more than `RECOVERY_NOTE_MAX_AGE_MS` (10 minutes) old (a rollback, a long outage) ends `unknown` as well, with no alert: the cause was downtime.
- `queued` or `rendered`, still within `expires_at`: the same BullMQ job id is awaited again. A render that finished while the bot was down is delivered at once, one still waiting or running is waited for, one the queue lost (a finished render is kept 3 minutes, a flushed Redis loses it) is rendered anew from the stored payload. The picture is then sent exactly once and recorded `delivered`. A recovered picture is not rebuilt from fresh calendar data (no request context after a restart) and is not pinned.
- A resumed picture keeps the slot and the payload hash stored on its row (`image_deliveries.slot`, `payload_hash`), so it is deduplicated and superseded exactly like a live one: the same picture asked again after a restart is `duplicate` (no second render, no second picture), and a newer one of the same slot replaces it.
- A rebuild that already started (a calendar write while the picture rendered) is recorded on the row before its render (`rebuilds`, the rebuilt `job_json` and `payload_hash`): a restart in between resumes the rebuilt `-r<N>` BullMQ job, never the stale one that had already finished. A rebuild is not started again after a restart.
- Past its bound, or without a payload (still `queued` or `rendered`): `expired`, ONE note to the user (`note_sent` guards a second one) saying the bot was restarting (`imageNoteInterrupted`), and NO timeout alert. A running process records `expired` itself when the bound passes, so a row still unfinished at start-up past its bound means the previous process stopped before the bound: downtime, not a slow render, and a deploy with a picture in flight must not open a render-timeout investigation. A row the previous process already ended as `expired` (it died before telling the user) still gets the "did not get ready in time" note.
- A delivery past its bound by more than 10 minutes ends `expired` silently: its note is claimed but not sent and no timeout alert is raised, because the user stopped waiting long ago and the cause was downtime, not a slow render. The same goes for a failed/expired row that was never told about days earlier.
- `failed` or `expired` with `note_sent = 0` (the process died between recording the outcome and telling the user): the one missing note is sent now. `note_sent` is claimed before sending, so a note is at most once. An `unknown` row never gets a note.
- An end the store refused to record (a locked database) is written again up to `RECORD_RETRIES` = 3 times, 1, 2 and 3 s apart, and once more, synchronously, by the graceful shutdown (`close()`; it stops at the first refusal, because SQLite has then already waited its 5 s busy timeout on that thread and the shutdown deadline is 8 s). Until it is written, the row still looks unfinished, so a restart in that window would expire or resume it a second time (a superseded older picture would be sent after the newer one); a note already sent meanwhile is claimed (`note_sent`) as soon as the write succeeds, and a refusal in the claim alone is tried again as the claim alone. What can still repeat the note or resume a stale picture: a process killed inside those seconds, or a store that refuses the retries and the shutdown write alike. A locked database is also reported as a `db_busy` timeout.

The repository enforces the single-send rule: `advance(id, 'sending')` only moves a row forward from `queued`/`rendered` and returns whether it won, and only the winner uploads; `expired`/`superseded` never apply to a row whose upload was claimed.

Known limits: a kill between the Telegram call returning and the `delivered` write leaves `sending`, so that picture is reported `unknown` even though it arrived (the price of never sending twice). A kill inside the tool call, before the `queued` row is written, loses the picture together with the turn that promised it; the user can ask again. A stale-data rebuild after a calendar write happens only in the live process; after a restart the stored payload is rendered as it was.

Reading an incident: `docker logs hypercal-bot 2>&1 | grep 'Image delivery outcome'` on `root@odroidn2` shows every outcome; `Image delivery failed` (error level) carries the stack of a failed one; the BullMQ side is `Image render failed` from the worker. A burst of `timed_out` means the host is overloaded (compare with the memory-pressure notes in [#800](https://github.com/alex-mextner/HyperCalendarBot/issues/800)), not that the tool is broken: the text answers still went out.

## Normal ship deployment

`gh ship <PR>` first delegates to the shared review, acceptance, merge and local-CI gates. The post-merge step loads its own code from the exact merged Git commit, so removing a PR worktree cannot remove the deployment runner. It reuses the local prebuilt-image fallback and repeats its exact-source tests; no `--skip-tests` is passed automatically.

The post-merge runner uses a nonblocking local release lock, then compares the production receipt, actual running image/revision, health and readiness. An already verified target is a no-op. A newer main is reported as superseded. An active hosted deployment remains its owner; an actual executed failing hosted step is not bypassed. A failed platform run with zero executable steps/runner or a bounded absence of a run may use the local gate. API errors are not treated as proof CI is down.

Since 2026-10-09 the `deploy` job runs on the odroid's self-hosted runner. While that runner is offline the job stays queued and the run is `in_progress`, so post-ship reports `hosted_pending` (exit 75) and the queued job deploys when the runner returns. A run that was cancelled, or whose build ran, is never treated as runner unavailability; deploy such a commit with `scripts/deploy-local-fallback.sh` directly.

Set the existing `HYPERCAL_BUN_BIN` operator variable before shipping when the default `bun` differs from the pinned local toolchain. `HYPERCAL_DOCKER_BIN`/`HYPERCAL_DOCKER_CONTEXT` are only for building with a real Docker Engine instead of Apple `container`: setting `HYPERCAL_DOCKER_CONTEXT` alone switches the builder to Docker, so do not leave a stale value (e.g. `colima`) exported — the post-merge runner inherits the environment. Status is recorded under the common Git directory as `post-ship-release.json`. `hosted_pending`, `busy` and `superseded` return exit 75, not a false deployment success. `ok (unverified)` remains runtime-only verification.

## Local deploy fallback

Use only when the hosted pipeline cannot deploy (no GitHub runner, or the odroid runner `odroid-hcb` is down) and the exact commit has been locally verified. The fallback builds Linux arm64 locally from a clean `git archive` and deploys to `root@odroidn2` (override with `HYPERCAL_DEPLOY_HOST`). The production host only loads a checksum-verified image; it never compiles source or runs the test suite. It stages the source and the image archive in a `0700` directory `/opt/hypercal/.incoming-<sha>-<time>-<pid>`, the same namespace as hosted deploys, and removes it on exit. Not `/tmp`: on the odroid that is a 1.9 GB tmpfs in RAM.

Local builder: on the dev Mac it is Apple's native `container` CLI (Homebrew `container`; run `container system start` if `container system status` reports it stopped), with no always-on Linux VM; on Apple Silicon the arm64 build is native. `container build --platform linux/arm64` builds the image, `container image save` exports an OCI image layout, and `scripts/oci-to-docker-archive.py --platform linux/arm64` converts that — verifying the digest of every blob it reads and keeping the config bytes, so the config digest is unchanged — into the `docker save` format that `scripts/release-artifact.py` and the server's `docker load` identity checks expect, including the OCI layout (`oci-layout`, `index.json` and an image manifest for the uncompressed layers) whose manifest digest becomes the image ID on the odroid's containerd image store (see Docker, "Image identity"). The local image is deleted after export. **Colima was removed from the Mac on 2026-09-26 (its VM disk kept growing) and is no longer a supported builder: do not reinstall it, Docker Desktop, OrbStack or another Docker VM for this.** A real Docker Engine elsewhere is still accepted via `HYPERCAL_BUILD_BACKEND=docker` (local Unix-socket context `HYPERCAL_DOCKER_CONTEXT`, default `default`, and CLI `HYPERCAL_DOCKER_BIN`); on an x86_64 Linux host it builds `--platform linux/arm64` only with binfmt_misc/QEMU arm64 emulation registered (for example `docker run --privileged --rm tonistiigi/binfmt --install arm64`), and much slower than native.

```bash
# The system Bun must be the pinned 1.4.2; otherwise point HYPERCAL_BUN_BIN at one.
scripts/deploy-local-fallback.sh

# If that exact commit already passed the full local gate in this incident/session:

```

The script keeps the actual running image under a timestamped rollback tag, takes a WAL-safe DB backup before restart, preserves host files, reapplies runtime directory ownership and recreates only the bot service. It requires exact `/health=ok`, `/ready=ok` or `ok (unverified)`, and the expected image identity (see Docker, "Image identity"). An unverified readiness response is recorded as such, not a completed live AI test. A failure restores the previous image and host files without overwriting newer calendar writes, and the rollback counts only when the restored container is the previous image answering `/health=ok` (readiness is logged, not required: an AI provider outage fails it for every image); otherwise the log says `ROLLBACK FAILED` and the bot may be down. Before any backup or restart, the schema gate below decides whether the release's migrations may activate unattended. No broad prune or shared-proxy reload is performed. The receipt is stored in `/opt/hypercal/releases/current.json`: `revision`, `config_digest`, `image_id` (the container's `.Image` the activator verified), `archive_sha256`, `ready`, `rollback_image`, `verified_at`. Normal gh-ship invokes this same fallback after its merge and hosted-run checks; manual use remains an operator recovery path. End-to-end AI verification remains tracked under #276.

### Disk space

`docker load` unpacks the whole archive before it registers the layers, so before loading the activator compares free space on the Docker root (`docker info` `DockerRootDir`) with twice the image's unpacked size (`image_bytes` in the artifact from `scripts/release-artifact.py`, the sum of the archive's files). Below that it stops before touching the service and prints both numbers, instead of failing halfway with `no space left on device` as the #599 release did on 2026-09-28 (#481).

After a verified release it keeps the five newest `rollback-<timestamp>` tags plus the current and previous release images, and removes every other tag of the release repository with `docker image rm` (never `-f`: Docker removes an image with its last tag and refuses one a container still uses). Each removal logs `IMAGE_RETENTION removed=<tag>`; a failure logs `IMAGE_RETENTION failed` and leaves the verified release in place. Other repositories on the shared host are never touched.

When the check refuses a release: save `df -h /`, `docker system df` and the image list under `/opt/hypercal/releases/prune-<date>/` (0700); keep the running image, `:latest`, the `rollback_image` named in `releases/current.json` and the newest rollback tags; `docker image rm <repo:tag>` the other `ghcr.io/alex-mextner/hypercalendarbot` tags; then re-run the failed deploy job. Never `docker system prune` or `docker image prune -a` on this host.

### Schema gate

`scripts/migration-gate.py check`, run by `deploy-prebuilt-image.sh` for hosted CI, the local fallback and gh-ship alike, compares `src/database/migrations.ts` of the running container with the release image (#589). When the file is byte-identical the release goes ahead. Otherwise it activates automatically only when every difference is a new migration entry appended after the shipped ones, which the database's `migrations` table (read through the running container) does not record yet, and whose `docs/reference/migrations/<name>.md` in the release image begins with exactly this front matter and has a non-empty body:

```markdown
---
migration: <name>
rollback-compatible: yes
data-deletion: no
---
```

- `rollback-compatible` says whether the previous image works on a database this migration has already changed. The automatic rollback relies on it. `no` needs a `## Rollback` section in the doc.
- `data-deletion` says whether the migration removes or overwrites data that cannot be rebuilt from the migrated database: a dropped column or table, deleted rows, or a flag cleared on rows whose earlier value mattered (063).
- Migration names are parsed strictly: each entry's `name:` is one single-quoted `[A-Za-z0-9_]` literal alone on its line. The names the release's module actually exports (read by importing it in a network-less container) must equal the parsed entries.
- Code outside the entries (imports, top-level statements, anything after the array) is fingerprinted as a whole. The array ends at the file's last line starting with `];`, so such a line inside a migration's template literal stays part of that migration.

A release that declares `rollback-compatible: no` or `data-deletion: yes`, changes code outside the entries, or ships a migration that the database records but the running image lacks (after an image-only rollback) needs a written, reviewed migration procedure, as for 062 and 063. The operator runs the activation by hand on the host and names the one transition that was reviewed. The refusal prints the pair, but it is the reviewed procedure that authorizes it:

```bash
HYPERCAL_REVIEWED_SCHEMA_TRANSITION="<running sha256>:<release sha256>" \
  bash "$STAGE/scripts/deploy-prebuilt-image.sh" /opt/hypercal "$STAGE" "$IMAGE" "$SHA" "$ARCHIVE_SUM" "$CONFIG_ID"
```

The two values are `sha256sum /app/src/database/migrations.ts` in the running container and in the release image. Hosted CI, the local fallback and gh-ship never set the variable. It never accepts a missing, empty or malformed doc; an edited, renamed, removed or reordered shipped migration (the runner would never run the edit); a `migrations.ts` that cannot be read or parsed; exports that differ from the source entries; or applied migrations or docs that cannot be read.

Every activation logs one audit line before the backup. Its keys are fixed:

- `SCHEMA_GATE decision=unchanged migrations_sha256=<sha256>`
- `SCHEMA_GATE decision=automatic|reviewed-override from=<running sha256> to=<release sha256>`, followed by one `migration=<name> doc=docs/reference/migrations/<name>.md doc_sha256=<sha256> rollback-compatible=yes|no data-deletion=yes|no` group per migration that the database does not record yet, or that it records while the running image lacks it. A reviewed override first logs the refusals it overrode as `Schema gate refusal: …` lines.

If a release that the override accepted with `rollback-compatible: no` fails verification, the script stops it (a release that already exited counts as stopped) and reads the `migrations` table with the previous image. It restores the previous image only when none of those migrations is recorded. Otherwise, or when the read fails, it starts the release again, logs `ROLLBACK_SKIPPED` (and `ROLLBACK FAILED` if the release does not start), and the operator follows the doc's `## Rollback` section. The database is never restored automatically.

### Image identity

The odroid's Docker (29.9.0) uses the containerd image store: `docker info` reports storage driver `overlayfs` with DriverStatus `[["driver-type","io.containerd.snapshotter.v1"]]`. It stays that way: Home Assistant and the other projects' containers live in that store. There, `docker image inspect <ref> --format '{{.Id}}'` and a container's `.Image` are the digest of the image's manifest (or of its index, for a multi-platform image), not the config digest that Docker's classic store reports.

A release archive is a `docker save` tar carrying both names: `manifest.json` points at the config blob, and the OCI layout (`oci-layout`, `index.json`) names one image manifest for the release tag (annotation `io.containerd.image.name`) whose `config` is that blob. `scripts/release-artifact.py` reads both from the archive, checks each blob against its digest and the manifest against the config, and reports `config_digest` and `manifest_digest`. The config digest stays the release identity: the activator's `CONFIG_ID` argument, `artifact.json` and the receipt's `config_digest`. `deploy-prebuilt-image.sh` reads the daemon's DriverStatus once and compares the loaded image's `.Id`, and the recreated container's `.Image`, with the one digest that store uses: `manifest_digest` on containerd, `config_digest` on the classic store. Anything else stops the deploy, before the backup for a bad load and with a rollback for a wrong container. The rollback check compares the restored container with the previous container's `.Image`, both read from the same daemon. The receipt records that `.Image` as `image_id`, which `scripts/post-ship-deploy.py` compares with the live container.

`release-artifact.py` therefore refuses an archive without that OCI layout, at build time in CI and in the local fallback. `docker save` writes it from Docker Engine 25 on, so a `HYPERCAL_BUILD_BACKEND=docker` builder needs Docker 25 or newer; `oci-to-docker-archive.py` writes it for the Apple `container` path. From a layout-less archive the containerd store would make up a manifest whose digest appears nowhere in the archive, so the deploy could not verify the loaded image.

The first odroid release, run 38018033717 on 2026-10-10 at about 03:07 UTC (`11bb45f7`), failed this way before the comparison was store-aware: `docker load` succeeded, then the activator stopped with `Loaded config identity mismatch` without touching the running container. Its archive's config digest is `sha256:37e13787…`, and its indexed manifest `sha256:f0828776…` (2234 bytes, `application/vnd.oci.image.manifest.v1+json`) is exactly the `.Id` the odroid reported for the loaded image.

### Deploy reliability (#823, #805)

One incident, 2026-10-24 (`evidence` in `~/.local/state/hcb-incidents/2026-10-24-deploy-818/evidence.md`): an HCB deploy overlapped an ESB deploy on the odroid, `/health` took longer than the old fixed 163 s poll, the activator rolled a healthy release back and the rollback destroyed the failed container's logs. The activator now does the following, all inside `scripts/deploy-prebuilt-image.sh` and its helpers (they ship in the release artifact, so a normal deploy updates them):

**Host deploy lock.** `scripts/odroid-deploy-lock.sh` (the same protocol is in ExpenseSyncBot) takes an advisory `flock` on `/run/lock/odroid-deploy.lock` before `docker load` and holds it through the container swap and verification. A second deploy, from either repository, WAITS (it logs `deploy-lock: ... held by: <repo> pid=... since=...` every 30 s) for up to `ODROID_DEPLOY_LOCK_MAX_WAIT` seconds (2400), then exits 75 so the job can simply be re-run. The kernel drops the lock when the holder dies, so a crashed deploy cannot wedge the host; `<lock>.owner` (repo, pid, process start ticks, start time) is informational and judged stale by pid + start ticks. The lock file is created mode 0666 so `www-data` (ESB) and root (HCB) can both open it. Manual check on the odroid: `flock -n /run/lock/odroid-deploy.lock true && echo free || cat /run/lock/odroid-deploy.lock.owner`.

**Health verdict.** `scripts/deploy-health.py` replaces the 15-poll timer. The release is accepted when the container is running, not restarting, not OOM-killed and its restart count is not climbing; `/health` is `ok`; `/ready` is `ok` or `ok (unverified)` (not required when it was already worse before this deploy, because an AI outage fails it for every image); and this holds for `HYPERCAL_HEALTH_STABLE` seconds (15). The window then also fails on a fatal log line (level >= 60) or more than 5 lines of level >= 50 since start; fewer are reported. A container that exited, was OOM-killed or restarted twice is `dead` at once, with no waiting. Otherwise the budget is `HYPERCAL_HEALTH_BASE_BUDGET` = 240 s, and it is extended only while the host is saturated (`/proc/pressure/io` some avg10 >= 20, or 1-minute load > 1.5 x cores) AND the container made progress (a new log line, or a changed probe answer) within `HYPERCAL_HEALTH_STALL` = 120 s, never past `HYPERCAL_HEALTH_HARD_CAP` = 900 s. A slow start under load is therefore not a failure; an alive-but-silent container, or one that is still not healthy at the cap, is `unhealthy` and rolled back as before. The verdict probes the container's own published port `http://127.0.0.1:3001` (the public ingress answers 502 instantly during a restart and is not what the release controls); `PUBLIC_DOMAIN` from `/opt/hypercal/.env` (last assignment wins, inline `# comment`, quotes and CR dropped) is used for one informational `PUBLIC_PROBE` line after verification. Baseline: measured starts were 45-77 s idle, 92 s for the old image under load.

**Failed-release evidence.** Before a rollback touches anything (before `docker stop`, before the force-recreate) `scripts/deploy-evidence.py failed` saves `/opt/hypercal/logs/failed-<sha12>-<UTC stamp>/` (mode 0700, root only): `container.log.gz` (the complete `docker logs`), `container.tail.redacted.log` (last 400 lines, at most 256 KiB, tokens/keys/passwords and message `text`/`caption`/`prompt`/`content` fields redacted), `inspect.json` (state, restart count, image, health, restart policy; never `Config.Env`), `receipt.json` (the last `releases/current.json`), `host-load.txt` (loadavg, PSI, `free`, `df`, `docker ps`, `vmstat`) and a one-line `state.txt`. The path is printed as `FAILED_EVIDENCE <dir>` in the job log. The same script copies the OUTGOING container's complete log to `/opt/hypercal/logs/release-<revision>-<stamp>/` before every swap, so the logs of every release survive its replacement.

**Log retention (nothing is deleted by a deploy or rollback).** After the commit point `scripts/log-retention.py --root /opt/hypercal/logs --alert` gzips old plain logs and deletes only when a criterion is violated, oldest first: managed bytes > 1024 MB, managed entries > 400, any file > 200 MB after gzip, or free space on the filesystem < 2048 MB / 5 %. It manages only `healthcheck*`/`backup*`/other top-level `*.log[.gz]` files and the `release-*` / `failed-*` directories (never `chats/`), and it never deletes the newest `release-*` (last deploy), the newest `failed-*` (last failure) or anything touched in the last 5 minutes. Exit 2 (criterion still violated with only protected entries left) and any deletion send a Telegram message to `BOT_ADMIN_ID` through `BOT_TOKEN` from `.env` (rate-limited to once per 6 h); free space within 2x of the floor warns early. This is also the disk-space watchdog: run it from root cron (`17 * * * * /opt/hypercal/scripts/log-retention.py ...`, see the install note below) so it does not depend on a deploy. Docker's own rotation stays `json-file` 50 MB x 5 per service in `docker-compose.yml` (`test/python/test_compose_logging.py`).
Root cron on the odroid runs the installed copy between deploys (the deploy installs `/opt/hypercal/scripts/log-retention.py`); add once, by hand: `crontab -l | { cat; echo '17 * * * * /opt/hypercal/scripts/log-retention.py --root /opt/hypercal/logs --env-file /opt/hypercal/.env --alert >/dev/null 2>&1'; } | crontab -` (alerts reach Telegram, so the output is not kept; running it by hand prints every action).


**Installing the activator after this change (root, by hand, with an instant rollback).** The wrapper has to know the new release files before the first release that ships them:

## Odroid runner

Hosted deploys run on a self-hosted runner on the odroid (#784), set up by hand when production moved there:

The one self-hosted job a pull request can cause is the per-PR stage QA, and it runs on its own runner and label, reached only through a `workflow_run` workflow from `main` that carries a SHA and never code: see "Stage QA". The repository's fork pull-request approval policy is `all_external_contributors`.
- Root activation wrapper: `scripts/odroid-activate-release.sh`, installed by hand after each change to it (deploys never update it):
  ```bash
  install -o root -g root -m 0755 scripts/odroid-activate-release.sh /usr/local/sbin/hypercal-activate-release
  ```
- `/etc/sudoers.d/hcb-runner` holds exactly:
  ```
  hcb-runner ALL=(root) NOPASSWD: /usr/local/sbin/hypercal-activate-release
  ```
- The job's only deploy step is
  ```bash
  printf '%s\n' "$GH_TOKEN" | sudo -n /usr/local/sbin/hypercal-activate-release "$RELEASE_SHA"
  ```
  with the job's `GITHUB_TOKEN` (`permissions: actions: read, contents: read, statuses: read`). The token is passed on stdin (`printf` is a shell builtin) and the SHA is the only argument.
- Release pin: after `actions/upload-artifact` in the GitHub-hosted `build` job, the step "Record the release artifact on the commit" posts a commit status on the SHA: context `release-artifact`, state `success`, description `artifact <id> sha256:<hex>` (upload-artifact v4.6.2 outputs the digest as bare hex, so the step adds the prefix), and target URL `https://github.com/<repo>/actions/runs/<run id>`. Only `build` has `statuses: write`. The deploy job can read statuses but not write them. Anything running on the odroid runner can upload more `release-<sha>` artifacts into the same run, but cannot post that status.
- Trust model: root trusts nothing from the runner except that SHA, and the token is used only to authenticate GitHub API calls. The wrapper (constants fixed in the file: repository `alex-mextner/HyperCalendarBot`, workflow `.github/workflows/deploy.yml`, `https://api.github.com`, `/opt/hypercal`, the image name):
  1. refuses unless `main` points at the SHA (`superseded: main is …`);
  2. reads the commit's statuses (newest first) and takes the newest `release-artifact` one. It requires state `success`, creator `github-actions[bot]`, a description matching exactly `artifact <id> sha256:<64 hex>` and a target URL that is a run of this repository. After "Re-run all jobs", the rerun's newer status names the rerun's artifact;
  3. fetches that artifact by id and requires: name `release-<sha>`, not expired, the digest the status names, and an upload by the run the status links to. That run must have `event` `push`, `head_branch` `main`, `head_sha` the SHA, `path` `.github/workflows/deploy.yml`, and this repository as both `repository` and `head_repository`. A `pull_request_target` run also reports `head_branch` `main`; the event and path checks exclude it;
  4. downloads the artifact zip, following at most 3 redirects itself and never sending the token past the first request, so it does not reach the storage host. It streams the zip into a fresh root-owned `0700` stage `/opt/hypercal/.incoming-<sha>-<time>-<pid>` (each file at most 4 GiB actually written) and refuses unless its sha256 equals that digest;
  5. extracts only the known release paths (`image.tar.gz`, `docker-compose.yml`, `Caddyfile`, `artifact.json`, the six core `scripts/` files the build copies, and the optional helper files named in the wrapper's `OPTIONAL_SCRIPTS` / `OPTIONAL`: `odroid-deploy-lock.sh`, `deploy-health.py`, `deploy-evidence.py` and `log-retention.py`), never names taken from the zip, then deletes the zip. The helpers are optional only for the wrapper: `deploy-prebuilt-image.sh` refuses a release that lacks one it needs, so a release built before them still unpacks but the new activator never runs without them;
  6. computes the archive sha256 and, with the staged `scripts/release-artifact.py`, the image config digest, and runs the staged `scripts/deploy-prebuilt-image.sh` with an empty environment at `nice 10` / `ionice -c2 -n7`. It returns the activator's exit code and always removes the stage. Refusals exit 2.

  Residual risk: code running as `hcb-runner` (a job, or a process a job left behind) can at most redeploy the release that main's GitHub-hosted build job recorded. Artifacts it uploads itself are never deployed, and it cannot supply files, scripts or checksums. The `release-artifact` status itself can be posted only by a token with `statuses: write`: the hosted build job, or a collaborator with write access (whose branch workflows can request that permission). Combined with a backdoor planted on the runner, a malicious write collaborator could still reach root here; fork pull requests cannot (their tokens are read-only). While the zip and the extracted image are both on disk, a deploy needs about twice the archive size free under `/opt/hypercal`.
- Secrets never go on a command line in a job that runs here: every local user can read process argument lists (`ps`, `/proc/*/cmdline`). The token reaches the wrapper on stdin. A job's environment is readable too (`/proc/<pid>/environ`) by anything running as `hcb-runner`. So a job on a self-hosted runner, in any workflow, gets no secret except its short-lived `GITHUB_TOKEN`. The deploy success and failure notifications (`BOT_TOKEN`, `BOT_ADMIN_ID`, `ADMIN_ALERT_TOKEN`) run in the GitHub-hosted jobs `notify-success` and `notify-failure`. `test/regressions/hosted-release-contract.test.ts` checks the secrets rule across all workflows. It and `test/python/test_odroid_activate_release.py` also look for the token in every process's argv during the run.
- The five self-hosted runner services on the odroid (the three other repositories' runners, `odroid-hcb` and the stage QA runner `odroid-hcb-qa`, see "Stage QA") have the systemd drop-in `50-yield-to-services.conf` (`CPUWeight=20`, `IOWeight=20`, `MemoryHigh=1200M`), and the microSD card `mmcblk0` uses the BFQ I/O scheduler (`/etc/udev/rules.d/60-mmc-bfq.rules`), so runner jobs and deploys yield to the live bots.
- The nightly backup is root cron `0 3 * * *` on the odroid, in its local time zone Europe/Berlin.

Its compose file is `/opt/hypercal/docker-compose.yml.moved-to-odroid`; `/opt/hypercal/MOVED-TO-ODROID.md` explains the move.

If the odroid wrote anything after 22:27 UTC (it serves all traffic since 22:30), copy the odroid's `/opt/hypercal/data` back to DO before starting there. Then rename the DO compose file back to `docker-compose.yml`, run `docker compose up -d` in `/opt/hypercal`, and point the DO Caddyfile back at `localhost:3001`. ## PR CI (full test, lint and typecheck gate)

`.github/workflows/pr-ci.yml` (job `test`) runs on every same-repository pull request to `main` the same gate that `deploy.yml`'s `test` job runs after merge: Bun 1.4.2, ffmpeg, `bun install --frozen-lockfile` as the first and only dependency install (a `package.json` change without the matching `bun.lock` fails the job, GH-870), Playwright `chromium-headless-shell`, full `bun test`, `bun run lint` and `tsc --noEmit`. Before this, a PR ran none of them and a red suite surfaced only on the push to `main`, after merge. The workflow has a read-only token, no secrets and no self-hosted runner, skips fork PRs, and cancels the previous run when a PR gets a new push. It replaces the branch-gated GH-359 stub `pr-gh359-validation.yml`, which was always skipped. `test/scripts/bun-version-pin.test.ts` keeps its Bun pin equal to the other pins; `test/scripts/workflow-install-order.test.ts` keeps this install step identical in `deploy.yml` and `pr-ci.yml`.

Apt is bounded in `pr-ci.yml`. On 2026-10-27 the azure Ubuntu mirror was slow, not down: the unbounded `apt-get update && install ffmpeg` step took 12 minutes 24 seconds in PR CI run 40573146944 (normally about 20 seconds) and was still running after 15 minutes in run 40573388213, with no log output; a first 300-second ceiling (run 40576298443) was exceeded while the log still showed ffmpeg's dependencies downloading one by one (about 14 MB in the last 17 seconds, a 5.8 MB package in 28), so the ceilings now sit above the slow case. The job has `timeout-minutes: 75`, a step writes `Acquire::Retries`/`Timeout` settings into `/etc/apt/apt.conf.d/99-ci-bounded` (which also bounds Playwright's own apt calls, each 25 minutes), ffmpeg is installed only when `ffmpeg -version` fails (`apt-get update` 300 s, install 1200 s, step 25 minutes), and the step then runs `ffmpeg -version` again: an unusable ffmpeg fails the job, tests are never skipped or stubbed. `deploy.yml`'s `test` job still has the old unbounded step because it did not stall.

This is the hosted check only. Agents still validate the exact PR head with the full suite on the owner's server (`server-run`, AGENTS.md § Heavy work runs on the server), never a full `bun test` on the shared workstation.

## Stage QA (per pull request, #840)

Every same-repository, non-draft PR gets a stage bot, `@HyperCalendarStageBot`, running that PR's exact head, and a QA run that drives it with real Telegram messages through qa-cli. The result is the commit status `stage-qa` on the head SHA. `gh ship` refuses unless it is green for the exact head; after that it simply deploys. Nothing of this sits inside the production deploy (`deploy.yml`, the activator and its wrapper know nothing about the stage). There is no Telethon session and no 2FA step: the QA account is the Telegram Web login qa-cli holds (`qa telegram status`), whose session file lives on the browser host. The job runs on the odroid (production host, where the stage bot runs); the browser runs on the server 65.21.40.51 because the odroid has no memory for it (see "Why the browser runs on the server").

**Pipeline.**
1. `.github/workflows/stage-build.yml` (`Stage build`, `pull_request`, GitHub-hosted arm64, no secret, no package access) marks `stage-qa` pending, builds the image of the exact head without pushing anything (`push: false`, tag `ghcr.io/alex-mextner/hypercalendarbot-stage:<sha>`), and uploads the artifact `stage-<sha>` with `image.tar.gz`, `stage-smoke-cases.json` and, when the repository has it, `stage-smoke-cases.replay.json`. Forks, drafts and bot-authored PRs are skipped. While `stage-qa.yml` is not on the default branch yet, no pending status is posted (bootstrap).
   The image tag is registry-qualified (`ghcr.io/alex-mextner/hypercalendarbot-stage:<sha>`) and never pushed: docker normalises a bare name to `docker.io/library/...`, and the archive check compares the exact name the archive carries (the first run of this workflow failed on exactly that with a bare tag).
2. `.github/workflows/stage-qa.yml` (`Stage QA`, `workflow_run` of `Stage build`) always runs the copy on `main`. Job `qa` ("Stage QA run") runs on the odroid's own runner labelled `stage-qa` and does one thing: `printf '%s\n' "$GH_TOKEN" | python3 /usr/local/lib/hypercal-stage/stage-qa-driver.py "$HEAD_SHA"`. Job `report` (GitHub-hosted, the only job with `statuses: write`) posts `stage-qa`: `success` as `passed cases=<n> run=<qa run id>`, `failure` for a failed case or build, `error` when the QA could not run (refused, not provisioned, the stage's image load or compose up failed, lock wait timed out, no driver), nothing for a superseded or cancelled run or for an exit code it does not know.
3. The driver (`scripts/stage-qa-driver.py`, installed root-owned by `install-stage-qa.sh` at `/usr/local/lib/hypercal-stage/`) first opens the ssh connection to the browser host (a key whose `authorized_keys` entry is `restrict,command="/home/ultra/hypercal-stage-qa/bin/stage-qa-browser"`: the only thing that key can do there is run the browser half with a commit SHA) and waits for the browser half to print `STAGE_BROWSER_LOCKED`, i.e. for the browser lock; only then it starts the wrapper with `sudo -n /usr/local/sbin/hypercal-stage-qa <sha>` (the runner user's only sudo right), feeds it the token on stdin, waits for its `STAGE_READY` line and forwards that payload (never the token) down the same connection. The order matters: the wrapper's 2400 s watchdog (`RUN_TIMEOUT`) starts when it holds the stage and host deploy locks, so no wait for the browser lock may happen after it, and a queued run holds no lock on the odroid while it waits. Driver timeouts (`/etc/hypercal-stage-qa/driver.json` keys, defaults): `lock_timeout` 3000 s for LOCKED (the browser half waits at most 2700 s; longer is exit 3), `ready_timeout` 5700 s for READY (stage lock 3000 s + host deploy lock 2400 s + margin; none is exit 1), `browser_timeout` 1800 s for the cases (smoke 1500 s; exceeding it is exit 3), `done_timeout` 600 s for the wrapper's teardown. Their sum, 11100 s = 185 min, must stay below the `timeout-minutes: 210` of the `qa` job. If the browser half ends before LOCKED its exit status is the verdict (75 when its lock wait ran out); if the wrapper ends before READY the driver closes the connection (the browser half exits and frees the lock) and returns the wrapper's status. The browser half's own `payload_wait` (7500 s) frees the lock if no payload ever arrives. The driver has no case floor of its own: it needs `status=passed` with `failed=0`, at least one case, and the requested `sha=` in the browser half's result line; the floor of 5 is enforced by the wrapper and the browser half.
4. The root wrapper (`scripts/odroid-stage-qa.sh`) trusts only that SHA and the token. It takes the stage lock (`/run/lock/hypercal-stage.lock`; PRs queue here), verifies through the GitHub API that the SHA is the head of an open, non-draft PR of this repository, finds the `Stage build` run itself (event `pull_request`, path `stage-build.yml`, success, this repository as head and base), takes its one `stage-<sha>` artifact (digest, size, run and SHA checked, redirect without the token), extracts only the fixed member names and checks the image with `release-artifact.py`. Only then it takes the host deploy lock (the one HyperCalendarBot and ExpenseSyncBot deploys use), re-checks the head, loads the image, builds `stage/bot.env` from the stage bot's token and an allow-list of AI-provider keys of the production `.env` (no Telegram, Google, e-mail, MTProto, inline or `PUBLIC_DOMAIN` key), wipes the stage SQLite file, starts `docker-compose.stage.yml` (project `hypercalstage`: own Redis with its own password, own data directory, `127.0.0.1:3002`, 768 MB, no webhook so it long-polls), waits for health with the multi-signal verdict of deploys, runs the guard (`stage-smoke.py guard`) and prints `STAGE_READY {json}` with the validated cases, then waits for `DONE` (or the end of the ssh connection). The stage instance exists only while both locks are held and never overlaps a production deploy.
5. The browser half (`scripts/stage-qa-browser.py`, the forced command of that key) takes the browser lock first (one Telegram Web session at a time; the other repository's stage run shares it) and prints `STAGE_BROWSER_LOCKED` (the only stdout line besides the result line), then reads the READY payload, checks it against its own config (stage username, deny list, case floor, required scenarios), runs the cases with `stage-smoke.py run` (`qa telegram chat send|wait|read` against the stage bot's numeric id; the replies are read from the web UI, so blockquote text is readable), writes the receipt and prints the last line `STAGE_QA_RESULT status=… sha=… cases=… failed=…`; its exit status is the verdict. When the driver's connection drops it stops the cases. The driver then sends `DONE` to the wrapper, which saves evidence and tears the stage down, always (pass, fail, cancel, timeout, dropped connection), and prints its own last line `STAGE_QA_RESULT ...` for the job.
6. Exit codes (the driver and the browser half use the wrapper's table): 0 passed; 1 health or a case failed (the PR is wrong); 2 refused (verification or a guard failed); 3 not runnable (`STAGE_QA_NOT_PROVISIONED`: config, key or `stage.env` missing, qa-cli not logged in, the browser host unreachable, silent for `lock_timeout` or `browser_timeout`, or its connection ended without a verdict or answered for another commit); 4 the stage infrastructure could not run (`docker load` or `docker compose up` failed on the odroid: the stage could not run, the cause may be infrastructure or image startup, and there is no test verdict; status `infra-error`, posted as `error`: `could not run: stage infrastructure failed (image load or compose up)`; #858); 75 a lock wait timed out (re-run the workflow); 76 superseded. The workflow itself adds 70 (the driver printed no result line: `error`).
   **Rollout order (exit 4 is produced by installed files, the workflow comes from `main`).** (a) Merge: the workflow on `main` then maps 4 to `error` and still maps 1 to `failure`. (b) Install `scripts/install-stage-qa.sh` on the odroid (the driver passes 4 through as `status=infra-error`; `stage-qa-run.sh` exits 4 instead of 1). Either order is safe: an old driver turns a 4 from a new wrapper into exit 1 (`failure`, as before), and an old wrapper still exits 1 for a failed image load or compose up (`failure`) until it is reinstalled. A new driver in front of a workflow older than this change would end with 4, which that workflow does not map: it posts nothing (the status stays pending and `gh ship` refuses), never a wrong verdict, so merge first. Exit 1 keeps meaning "the PR is wrong": health failing after the stage started, the run budget, a failed case.
7. Logs are never deleted by a run. Teardown first copies the stage container's complete log to `/opt/hypercal/stage/evidence/release-stage-<sha12>-<stamp>/` and, after a failure, a redacted failure bundle `failed-<sha12>-<stamp>/` (same helper as deploys, a separate root so the production evidence's "newest" protection is untouched); the bot's own files stay in `/opt/hypercal/stage/logs`; the browser host keeps `~/.local/state/hypercal-stage-qa/receipts/<sha>.json` (case names, counts and latencies only). Rotation is by size and free space only (`log-retention.py`), see Install.

**Cases.** `scripts/stage-smoke-cases.json` is the PR's own list (a PR may add cases, e.g. for the behaviour it changes). The browser host and the wrapper both enforce a floor the PR cannot go below: at least 5 cases and the names `start`, `ping`, `today-read-only-calendar`, `simple-intent-phrase`, `validation-search-without-query`. `expect`/`forbid` are regexes over the reply text, `max_first_reply_s` bounds latency. No case changes the calendar. History replay hook: a file `scripts/stage-smoke-cases.replay.json` with cases of the same schema (plus an optional `source` label) is built into the artifact and appended after the base cases; it cannot reuse a base name or fill the floor. The builder for the real historical corpus only has to write that file; nothing depends on it today.

**Guards.** Odroid side (`stage-smoke.py guard`): the target username comes from `stage.env`, differs from `HyperCalendarBot` and the production env's `BOT_USERNAME`, contains `stage` or `stg`, its token's bot id differs from the production token's, and Telegram's `getMe` for that token answers with that username. Browser-host side (`stage-qa-browser.py` and `stage-smoke.py run`): the username must equal the one in that host's own config, must not be on its deny list (`HyperCalendarBot`), must contain `stage`/`stg`, and `qa telegram chat` itself refuses writes to anything that is not a bot chat. An empty or shorter list than the floor is refused, never passed.

**Trust boundary (public repository).** A PR's code runs only on GitHub-hosted runners (build) and, as a container with the stage bot's token and the AI keys, on the odroid. It never runs as a process on the QA runner, the odroid host or the browser host: `stage-qa.yml` checks nothing out and downloads nothing, its YAML always comes from `main`, the driver, the browser half and the wrapper come from a reviewed `main` checkout (the driver and the wrapper are root-owned), and `test/regressions/stage-qa-workflows.test.ts` plus `hosted-release-contract.test.ts` pin that. The runner user can run nothing as root except the wrapper (sudoers) and nothing on the browser host except one forced command that accepts a commit SHA and a READY payload; the GitHub token never leaves the odroid. The PR supplies an image and a case list (data, validated on both sides; texts are passed to qa-cli as one argv element, never through a shell). Residual risk: a collaborator with write access (the same people who can already push workflows that request `statuses: write`) controls the image and the case list of their own PR; fork PRs are excluded by the same-repository checks at the workflow, the wrapper and the ship gate, and by the `all_external_contributors` approval policy. `gh ship` does not trust the status alone: `scripts/stage-qa-gate.py` requires creator `github-actions[bot]`, a description naming the run, and that run to be a `workflow_run` run of `stage-qa.yml` for the exact head with a successful `Stage QA run` job; a status a PR workflow posts cannot satisfy that.

**How `gh ship` binds the QA run to the PR head (#865).** `.claude/scripts/pr-ship.sh` runs `scripts/stage-qa-gate.py` from `origin/main`, never from the PR checkout, so a PR cannot edit its own gate. The gate accepts the status only when: the PR is open, non-draft, same-repository and the head it is asked about; the newest `stage-qa` status on that head is `success`, created by `github-actions[bot]`, described `passed cases=<n> run=<id>` with the exact target URL of that run; the run is `.github/workflows/stage-qa.yml`, event `workflow_run`, completed/success, `repository` and `head_repository` this repository and `head_branch` the default branch; the run has exactly one job `Stage QA run`, completed/success, of that run and attempt, whose steps are `Set up job` (1) and `Run the stage QA through qa-cli` (2, success); and the tested head is the one the runner printed for that step. The last point cannot use the run's REST `head_sha`: a `workflow_run` run reports the default branch commit there (with empty `pull_requests`/`referenced_workflows` and the title `Stage QA`), the tested PR head is only an event value the workflow hands to the step as `HEAD_SHA`. The gate therefore reads the head of the QA job's log (`gh api repos/<repo>/actions/jobs/<id>/logs`, which follows GitHub's signed redirect; at most the first 256 KiB, in memory, never printed) and takes the first `##[group]Run ` group, the runner's header of step 2, which the runner writes before the trusted shell executes anything: exactly one `  HEAD_SHA: <40 lowercase hex>` line in its `env:` block must equal the PR head. Whatever the driver or the stage bot prints afterwards (including a forged header) is never read. A missing or duplicated header, another SHA, an unreadable, expired (GitHub deletes logs after its retention period; re-run Stage QA), empty, truncated or unrecognised log, or any API error refuses the ship (exit 1 for evidence that does not match, exit 2 when the gate cannot evaluate); there is no fallback to a weaker check, and a receipt left on the browser host is never evidence. The log binding exists because PR 853's cleaner route, naming each run `Stage QA <sha>` through `run-name` and binding `display_title`, cannot bootstrap (the workflow is always `main`'s copy, so the PR that introduces it still runs with the plain title); once that lands and has produced runs, the gate can bind `display_title` instead and drop the log read. The status time window is only corroboration (a forged `success` can land inside it): the gate also reads the header of the report job's first step, `Post the stage-qa status`, and requires its env block to declare each of `HEAD_SHA` (the PR head), `RUN_ID` (the run in the status), `BUILD_CONCLUSION=success`, `QA_RESULT=success`, `QA_RC=0` and `QA_CASES` (equal to the `cases` in the status) exactly once, so a forged status cannot claim a pass the workflow did not decide (for example the QA step exiting 0 with zero cases, which the workflow reports as `error`).

If the stage infrastructure is broken, fix it; the ship gate has no bypass. The repository owner can still merge by hand with `gh pr merge --squash --match-head-commit <sha>`, and the normal deploy follows. To revoke the QA login: Telegram, Settings, Devices, terminate the Web session; then `qa telegram login` again on the browser host. A dedicated QA Telegram account would keep this off the owner's personal account; qa-cli supports it by logging in with that account instead.

## bun lockfile and --frozen-lockfile

The committed `bun.lock` is frozen-installable on linux (verified 2026-10-27 with Bun 1.4.2: `bun install --frozen-lockfile` exits 0 and leaves `bun.lock` byte-identical, and the same command exits 1 with `lockfile had changes, but lockfile is frozen` once `package.json` gains a dependency the lock lacks). The earlier note that a macOS arm64 lockfile fails on linux came from platform-specific optional dependencies (`@rollup/rollup-darwin-arm64` vs `@rollup/rollup-linux-x64-gnu`) that the manifest no longer contains. If a new dependency brings back a platform-dependent lock, regenerate `bun.lock` with a normal commit; do not weaken the CI check.

- **CI** (linux, `deploy.yml` and `pr-ci.yml`): `bun install --frozen-lockfile` as the first install. Never run a plain `bun install` before it: that rewrites `bun.lock` in the runner and the frozen check then passes on a lockfile nobody committed (GH-870). The install keeps lifecycle scripts, so `scripts/install-git-hooks.sh` runs as on a developer checkout.
- **Docker** (linux): `bun install --ignore-scripts` with the copied `bun.lock` — respects the lockfile's version pins and skips the lefthook postinstall (no git in the image).
- **Local**: `bun install --frozen-lockfile` to reproduce CI; a plain `bun install` only when you are deliberately updating `bun.lock`.
- **Local release fallback** (`scripts/deploy-local-fallback.sh`): `bun install --frozen-lockfile --ignore-scripts` — the same frozen check, without lifecycle scripts because it builds a release, not a developer checkout.

## bun install --production in Docker

`bun install --production` with an **existing lockfile** always acts as `--frozen-lockfile` and
fails if the lockfile format differs. **Never use `--production` with `COPY bun.lock`.**

For a prod-deps Docker stage:
```dockerfile
COPY package.json ./          # no bun.lock
RUN bun install --production --ignore-scripts
```

## Docker prod data volume ownership

The bot runs as `botuser` (uid=999) inside the container. The data volume on the host
(`/opt/hypercal/data/`) must be owned by uid 999, otherwise SQLite throws `SQLITE_READONLY`.

```bash
# Find actual botuser UID:
docker run --rm --entrypoint id ghcr.io/alex-mextner/hypercalendarbot:latest
# Fix ownership (replace 999 with actual UID):
chown -R 999:999 /opt/hypercal/data/
```

## Database backups

`scripts/backup-db.sh` (root cron `0 3 * * *` and every deploy) and the bot's own daily backup write full calendar-database copies into `/opt/hypercal/data/backups/`. Each copy holds every user's private data, so files are `0600` and the directory `0700`, owned by the container user `999`, which must keep write access. The cron script writes the copy inside the container with umask `077`, then enforces and checks both modes on the host; a copy it cannot restrict is deleted and the script exits non-zero, which also stops a deploy. Each run also restricts older copies left `0644` by earlier versions. A deploy runs the previously installed script, so the backup taken by the deploy that first ships a change to it follows the old rules until the next run. Inspect backups with `stat` only; never open their contents on a shared host.

## Google event id backfill (#875)

`scripts/backfill-google-event-ids.ts` relinks bot rows (`events`, `participant_google_sync`) that have no Google event id although their Google copy exists: a lost insert answer, or a link a disconnect cleared. It lists the user's primary calendar, then matches a copy to a row only when the match is the single candidate on both sides: first through the `hypercalendarbot_event_id` marker the copy carries, then, for rows that claim a copy (not `local_only`) and found none, through (summary, start, end) on copies that carry no marker of a live row. It never writes to Google, never changes event text and prints counts only (no titles, ids or user ids).

```bash
# Dry run: database opened read-only, nothing written (a refreshed Google access token is not saved either).
ssh root@odroidn2 'docker exec hypercal-bot bun run scripts/backfill-google-event-ids.ts'
# Apply: first a verified backup, then only the missing ids and one sync_log row per link; run the dry run first and keep its output.
ssh root@odroidn2 'docker exec hypercal-bot bun run scripts/backfill-google-event-ids.ts --apply'
```

The apply writes `/opt/hypercal/data/backups/google-id-backfill-<UTC stamp>.db` (`VACUUM INTO`, `quick_check`, mode `0600`, never overwrites a file; `--backup PATH` names another) before the first write, then one transaction per user that sets `google_event_id` where it is still empty and no row of any user points at that copy (two users can share one Google calendar), and logs a `sync_log` row (`direction = pull`, `action = update`, `details` `{ "reason": "google_id_backfill", "via": "marker" | "slot", "kind": "owner" | "participant" }`). A row that changed between the read and the write is counted in `skippedChanged` and left alone. It is idempotent: linked rows are no longer candidates, and the output ends with the counts that remain.

Output lines (`label` = `dry-run`, or `before`, `backup`, `apply`, `after`): `googleListed`, `googleBotCopies`, `alreadyLinked`, `looseCopies`, `unlinkedRows`, `linkableByMarker`, `linkableBySlot`, `ambiguous` (more than one candidate: left alone), `copiesWithoutRow` (a copy of an event that is deleted in the bot or not this user's), `extraCopiesOfLinkedEvent` (a duplicate copy in Google of an event whose row points at another copy; the bot never deletes it, remove it by hand in Google Calendar), `rowsWithoutCopy`.

A user whose Google read fails (revoked token, API error) is reported on stderr as `{"label":"user-failed","user":N,"error":"<error class>"}` and skipped, and the exit code is 1; a dry run still prints the others, but `--apply` then writes nothing (`refused`), because a user who could not be read cannot claim their copies. A copy two users' plans both match, or one plan found ambiguous (two users on one Google calendar), is linked to neither and counted in `ambiguous` (rows and copies are counted, so one contested slot can add 2). A copy is matched by summary and time only when it carries no bot marker at all, and such a match is only reported (`linkableBySlot`): `--apply` writes it only with `--include-slot-matches`, because an unmarked event may be one the user made in Google themselves and linking it would let the bot edit or delete it. `--backup PATH` is used as given: the script creates and restricts (`0700`) only the default `backups/` directory, never one the operator named, and the parent of a named path must exist.

## Migration renumbering hazard

If a migration is renumbered (e.g. `042_foo` -> `043_foo`), the existing production DB has the old
name recorded and the new code tries to apply it again. **Never renumber existing migrations.**

Fix if already happened:
```bash
docker run --rm -v /opt/hypercal/data:/data ghcr.io/alex-mextner/hypercalendarbot:latest \
  bun -e "
import { Database } from 'bun:sqlite';
const db = new Database('/data/calendar.db');
db.run('INSERT OR IGNORE INTO migrations (name) VALUES (?)', ['043_new_name_here']);
db.close();
"
```

## ntgcalls — Build from Source (voice calls only)

ntgcalls v2.1.0 has a bug: P2P calls connect but audio is silent.
Fix: `NativeNetworkInterface::UpdateAggregateStates_n()` never calls `OnNetworkAvailability(true)`.
Patch: `scripts/ntgcalls-fix-network-state.patch`.

**The compiled `.so` is NOT in git (venv/ is gitignored). Must rebuild on each server.**

On every new Linux server:

```bash
# 1. Install uv (if not present)
curl -LsSf https://astral.sh/uv/install.sh | sh
```

- The build aborts if the P2P audio patch does not apply — it never installs an unpatched binary
- Build deps: CMake 3.20+, git, Python 3.12, 5GB RAM min

## MTProto service tier

> **2026-09-30:** restored behind `ServiceTier`, with no service sends (#753).

`src/services/telegram-session/service-tier.ts` decides once at startup, fail-closed: the tier is on only
when `MTPROTO_API_ID` / `MTPROTO_API_HASH` are set, `MTPROTO_SERVICE_USER_ID` is a positive integer,
`data/voice_caller.session` exists, and `scripts/check-session.py` reports exactly that ID. The log shows
one line: `MTProto service tier enabled` (with `accountId`) or `MTProto service tier disabled` with
`reason` = `service_user_id_unset` | `service_user_id_invalid` | `api_credentials_missing` |
`session_missing` | `probe_failed` | `identity_mismatch`.

Enabled, it resolves @usernames, looks profiles up, lists group members, syncs birthdays (daily
`birthday-sync-tick`) and places voice-call reminders (`call-reminders` queue; `DEEPGRAM_API_KEY` for live
calls, `DISABLE_VOICE=true` to opt out). It never sends messages: invitations go Bot API → the inviter's own
`/connect_telegram` session → a deep link to the inviter; proposals and secretary DMs go Bot API → a deep
link to the initiator. Disabled,
`find_user` / `send_invitation` use the local `users` table and otherwise the picker, group members come
from `group_members`, and birthday sync and voice calls are off.

**Prod:** `MTPROTO_SERVICE_USER_ID` was never set, so the tier is off. To turn it on the owner designates a
service account (Telegram may block such accounts), runs `venv/bin/python scripts/pyrogram-auth.py`
interactively to create `data/voice_caller.session`, sets `MTPROTO_SERVICE_USER_ID` (+ `DEEPGRAM_API_KEY`)
in `/opt/hypercal/.env`, and recreates the bot container. Never build the service session from a user's
stored `/connect_telegram` authorization; do not rotate or revoke unrelated user sessions.
